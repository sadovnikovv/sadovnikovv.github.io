33.4.1. AI Fluency: Framework and foundations

ИИ-грамотность

Речь не о изучении устройства ИИ, а о сотрудничестве с ним.

ИИ-грамотность - работать с ИИ эффективно, результативно, этично и безопасно.

Основа - четыре компетенции: Delegation, Description, Discernment, Diligence.

  • Навыки должны оставаться актуальными при смене моделей.
  • Это практика, а не знание.

Упражнение по мотивам курса

Условие
  1. Оцените себя по каждой из четырёх компетенций: новичок, развиваюсь, уверенно.

Критерии проверки:

  • Каждая оценка обоснована примером.
Зачем нужна ИИ-грамотность

Три способа работы с ИИ: автоматизация (ИИ выполняет задачу по инструкции), усиление (совместная работа), агентность (ИИ работает самостоятельно по вашему поручению).

Каждый способ требует своих навыков контроля.

Грамотность - это понять, в каком режиме вы сейчас.

  • Автоматизация - самый частый режим.
  • Агентность требует больше проверок.

Упражнение по мотивам курса

Условие
  1. Разложите свои задачи по трём способам.

Критерии проверки:

  • Для агентных задач есть правила проверки.
Рамка 4D

Delegation - что делать самому, что с ИИ.

Description - как ясно объяснять задачу.

Discernment - как критически оценивать результаты.

Diligence - как отвечать за результат.

Компетенции работают вместе и переходят одна в другую.

  • Перед задачей - делегирование.
  • После - оценка и ответственность.

Основы генеративного ИИ

Генеративный ИИ создаёт новое содержимое, а не только анализирует существующее.

Языковые модели предсказывают следующий фрагмент текста; их возможности основаны на трансформерах.

Понимание процесса помогает предвидеть ошибки.

  • Модель не «знает», а предсказывает.
  • Это объясняет уверенные, но неверные ответы.

Упражнение по мотивам курса

Условие
  1. Объясните своими словами, почему модель может уверенно ошибаться.

Критерии проверки:

  • Объяснение связано с предсказанием следующего фрагмента.
Возможности и ограничения

33.4.3. Building with the Claude API

Путь запроса к Claude API

Каждый запрос проходит пять этапов: запрос к вашему серверу, запрос от сервера к Anthropic API, обработка моделью, ответ серверу, ответ клиенту.

Ключ API нельзя использовать в браузере или мобильном приложении: его видно и легко украсть. Запросы идут через ваш сервер, где ключ хранится безопасно.

Такое устройство полезно для архитектуры и для поиска проблем: по этапам видно, кто виноват в ошибке.

  • Секретный ключ - только на сервере или в переменных окружения.
  • Разделение клиента и сервера упрощает контроль расходов.

  3. Отметьте, где логируются ответы и ошибки.

Критерии проверки:

  • Ключ не появляется на клиенте.
  • Каждая ошибка привязана к этапу.

API оплачивается отдельно от подписки Claude. Даже при платном тарифе в консоли нужен положительный баланс; в ряде тарифов есть ежемесячные кредиты, которые активируются привязкой организации к тарифу.

Шаги: войти в консоль, проверить баланс, создать ключ с понятным именем и сроком действия.

Ключ без кредита создаётся, но запросы с ним не выполняются.

  • Давайте ключу осмысленное имя и срок.
  • Один ключ - одно место использования; при утечке отзывайте.

33.4.5. Claude Code 101

Что такое Claude Code

Claude Code - агентский инструмент для программирования: понимает кодовую базу, правит файлы, запускает команды и работает вместе с привычными инструментами разработчика. Доступен в терминале, VS Code, JetBrains, настольном приложении Claude и в веб-версии.

Главное отличие от обычного чата Claude: у Claude Code есть прямой доступ к файлам, терминалу и проекту. Не нужно копировать код туда-обратно: он сам выполняет работу.

Ключевое понятие - агент. Это программа, которая взаимодействует со средой и совершает действия ради поставленной цели. Внутри - языковая модель, работающая в цикле в реальном времени. Агент может пользоваться инструментами, внешними сервисами и даже другими агентами.

  • Читает и разбирает проект: просите объяснить функцию или проследить ошибку по коду.
  • Правит файлы по всему проекту: рефакторинг функции и обновление всех ссылок на неё.
  • Запускает команды терминала: сборку, тесты, установку пакетов, и смотрит на результат, чтобы решить, что делать дальше.
  • Работает как собеседник, а не как справочник: можно уточнять, перенаправлять, прерывать.

Как работает Claude Code

Режим работы удобнее всего описывать агентским циклом: вы вводите запрос, агент собирает нужный контекст, модель отвечает текстом или вызовом инструмента, агент выполняет действие (правит файл, запускает команду), проверяет результат и решает - закончить или повторить попытку. В любой момент можно вмешаться, добавить контекст или прервать.

Окно контекста - это «память» сессии: история диалога, содержимое файлов, вывод команд. Когда место кончается, Claude Code автоматически сжимает разговор, оставляя главное.

Инструменты - основа агента. Обычный чат только принимает текст и возвращает текст, а инструменты дают агенту право действовать: читать файлы, искать, запускать команды, обращаться к сети. Агент сам выбирает инструмент по смыслу задачи.

Разрешения определяют, что выполняется без вопроса. Режимы от «спрашивать всё» до автономной работы; выбор режима - ключ к безопасной работе.

  • Наблюдение, план, действие, проверка - повторите цикл на листе бумаги и посмотрите, на каком шаге обычно перестаёт работать ваша работа с ИИ.
  • Контекст - управляемый ресурс: команды /context, /compact, /clear (подробнее в главе про контекст).
  • Детерминизм дает hooks: если что-то должно случаться всегда, его место - не в тексте просьбы, а в хуке.

Первый запрос и режимы работы

Хороший первый запрос содержит цель, границы и критерий готовности. Вместо «поправь баг» - «найди, почему тест X падает на CI, но не локально; исправление только в файлах папки src/timer; покажи diff».

Курс разбирает режимы: ручной (спрашивать о каждой правке), accept edits (правки файлов идут автоматически, команды - по решению режима), автоматический режим и Plan Mode (сначала план, потом код).

Правки принимаются не целиком, а по смыслу: читайте diff, прежде чем оставлять изменения.

  • Правки файлов и запуск команд - разные уровни опасности, режим разрешений их различает.
  • План в Plan Mode - это контракт: если план неверный, его дешевле поправить до кода, чем после.

Рабочий процесс: Explore, Plan, Code, Commit

Рабочий цикл, который рекомендуют почти все продвинутые практики: сначала исследовать (Explore) - агент читает код, находит зависимости, отвечает на вопросы; затем планировать (Plan) - получаем план и согласуем; затем кодить (Code) - правки с проверкой после каждого шага; затем фиксировать (Commit) - маленький осмысленный коммит с хорошим сообщением.

Исследование до кода экономит контекст и деньги: преждевременная правка заставляет агента читать больше и переписывать работу.

Проверка после правки - не опция, а часть цикла: тесты, сборка, запуск, явный diff. Если проверки нет, цикл не завершён.

Коммит - точка, к которой можно вернуться. Агент умеет готовить сообщение коммита по diff, но авторство и проверка остаются за человеком.

Управление контекстом

Контекст - рабочая память Claude. Каждый прочитанный файл, запущенная команда, сообщение занимают место. Когда контекст заполнен, качество падает: агент забывает детали и путает файлы.

Две главные команды: /compact - сжимает сессию в резюме (при работе над той же задачей), /clear - начинает с нуля (при переходе к новой задаче). /context показывает, сколько занято и что занимает места больше всего.

Конкретный запрос экономит контекст: расплывчатый заставляет агента самому копаться в проекте, что стоит дороже, чем подробная формулировка.

MCP-серверы, субагенты и размер истории тоже влияют на контекст: лишние серверы выключайте, а на поисковые задачи отправляйте субагентов - их подробная работа не попадает в основной контекст.

  • /compact - для продолжения той же задачи, /clear - для новой: это правило, а в не «на что хватит времени».
  • Что должно помниться между сессиями, пишите в CLAUDE.md, а не надейтесь на историю.

Условие

Проверка изменений (code review)

Сессия, которая писала код, - не лучший судья своих изменений. Правило: сначала посмотреть diff самому, потом попросить Claude пересмотреть работу из «чистого» контекста, без истории этой сессии.

/diff открывает интерактивный просмотр незафиксированных изменений: пофайловое сравнение до и после. В первую очередь проверяйте три вещи: правки, о которых вы не просили; ослабшие тесты (пропущенные, удалённые проверки); изменения зависимостей и настроек.

Проверка «чистым» субагентом ловит то, что сессия считает своим успехом. Это пример того же принципа: код оценивают независимо от автора.

  • Не просите и не принимайте правку без diff.
  • Ослабленные тесты - скрытый риск: зелёные тесты, которые больше ничего не проверяют.
Попробуйте

В своей сессии откройте /diff и просмотрите изменения файл за файлом. Отметьте правку, которую вы не просили, и ослабленный тест, если он есть.

CLAUDE.md: постоянная память проекта

CLAUDE.md - файл с правилами и фактами о проекте, который агент читает в начале каждой сессии. Он решает проблему «агент не знает, что у нас так принято».

Не дублируйте в CLAUDE.md то, что видно из кода. Пишите то, что неочевидно и повторяется: почему выбрана технология, где лежит конфигурация стенда, какие ограничения у оборудования.

  • Обновляйте CLAUDE.md, когда повторяете одно и то же исправление второй раз.
  • Большой файл тоже ест контекст: держите его кратким и по делу.

Субагенты

Субагент - помощь Claude Code, которая работает в отдельном окне контекста и возвращает в основной разговор только сводку. Все промежуточные чтения, поиски и вызовы инструментов остаются в его собственном транскрипте.

Это решает главную проблему длинных сессий: основной контекст не забивается «шумом дороги». Цена - основной разговор не видит, как получен вывод.

У Claude Code есть встроенные субагенты (например, общий исполнитель для многошаговых задач и поисковый для исследования кода) и свои собственные, с отдельными инструкциями и правами.

  • Вопросы вида «где находится X?» - типичное дело для субагента: нужен ответ, а не путь.
  • Свой субагент - это отдельный файл-инструкция и, если нужно, отдельный набор разрешений.

Скиллы

Скилл - папка с инструкцией (SKILL.md) и, при необходимости, скриптами и шаблонами, которую Claude Code загружает подходящей задаче. Это способ не объяснять одно и то же каждый раз.

Скиллы лучше подходят для процедур: «как собирать отчёт по испытаниям», «как проверять DRC», «как оформлять коммит». В отличие от CLAUDE.md, который действует всегда, скилл включается по ситуации.

Скилл можно распространять: опубликовать в плагине или поделиться папкой с командой.

  • Один повторяющийся алгоритм = один скилл.
  • Скрипты внутри скилла делают работу детерминированной - это надёжнее, чем надеяться, что модель выполнит шаги вручную.

MCP: внешние инструменты и данные

Model Context Protocol - стандарт, по которому Claude Code подключается к внешним сервисам. Сервер MCP предоставляет инструменты (функции), ресурсы (данные) и промпты (готовые сценарии).

Так агент может работать с базой данных, трекером задач, документацией или вашим собственным стендом, не переписывая Claude Code.

Для инженера это путь к интеграции с измерительными приборами, EDA и системами управления версиями: CLI или локальный сервис оборачиваются в MCP-сервер.

  • Начинайте с одного сервера под реальную задачу; каждый сервер немного ест контекст.
  • Сервер MCP выполняет действия от вашего имени - проверяйте, к каким данным он имеет доступ.

Hooks: действия, которые случились обязательно

Hooks - команды, которые Claude Code запускает в определенных точках жизненного цикла. Их главное свойство - детерминизм: они срабатывают всегда.

Просьба в CLAUDE.md «запускай prettier после каждой правки» обычно выполняется, но иногда нет. Хук делает так, чтобы выполнялось каждый раз без исключений.

Типичные применения: автоформатирование после правок, журнал выполненных команд, блокировка опасных операций, уведомление о завершении задачи.

Настраиваются в settings.json: событие, необязательный matcher (какие инструменты), команда. Популярные события: PreToolUse, PostToolUse, UserPromptSubmit, Stop, Notification. Код выхода 0 - продолжать, 2 - заблокировать и передать сообщение агенту как обратную связь, другое - некритичная ошибка для вас.

  • Всё, что должно быть гарантировано, - в hook, а не в тексте инструкции.
  • PreToolUse с кодом 2 - это блокировщик: агент получит причину и сможет исправить запрос.

33.4.6. Claude Code in action

Управление длинными сессиями

Короткую задачу легко: спросил, сделал, проверил. Долгие задачи (рефакторинг по десяткам файлов, новая функция на часы) ломают этот подход: чем больше шагов, тем больше поводов увести агент не туда.

Два навыка: заранее ограничить объём работы и управлять ходом сессии. Первое делается Plan Mode: агент исследует код без правки и выдаёт план, вы его читаете, а не проглядываете, и просите доработать до начала работы.

Второе - управление в процессе: сжатие контекста (/compact), прерывание, уточнения по ходу, а при крупных сбоях - откат к более раннему сообщению (rewind).

  • План, прочитанный внимательно, экономит часы правок.
  • Автоматическое сжатие может потерять важную деталь, поэтому важное фиксируйте в файлах проекта, а не в истории чата.

Задание по мотивам курса: длинная задача с планом

Условие

Возьмите задачу на несколько часов и проведите её через весь цикл.

  1. В Plan Mode сформулируйте цель и ограничения; прочитайте план и внесите минимум три правки.
  2. Утвердите план и ведите сессию: после каждого завершённого пункта проверяйте результат.
  3. В конце сравните результат с планом: что получилось иначе и почему.

Критерии проверки:

  • Плана до кода в истории есть, и он отличается от первого черновика.
  • Каждый шаг проверен до перехода к следующему.
  • Подсчёт потраченного контекста и денег известен.
CLAUDE.md, который соблюдается

Классическая ловушка: CLAUDE.md растёт с каждым инцидентом и в итоге игнорируется частично. Это не ошибка Claude, а свойство файла: каждый пункт конкурирует за внимание с остальными.

CLAUDE.md - не конфигурация, а рекомендация. Для правил, которые нарушать нельзя (например, «никогда не пушить в main»), нужен hook с блокировкой. Это реальное принуждение, а не вежливая просьба.

Файлов может быть четыре уровня: корень проекта, каталог, ваш личный, пользовательский. Все они загружаются вместе. Правило: общее - в проектные, личное - в личные, запреты - в hooks.

  • Перед каждым новым правилом спросить: это руководство или жёсткий запрет?
  • Длинный CLAUDE.md - сигнал переносить процедуры в скиллы, а запреты - в хуки.

  • Нарушить запрет невозможно, даже если модель забыла инструкцию.
  • Файл стал короче и не потерял смысла.
Скиллы проверки

Самый полезный первый скилл - проверка собственной работы. Обычно проверка зависит от вашей памяти и времени: агент закончил, вы вспомнили, что надо посмотреть.

Скилл проверки срабатывает сам: после завершения правки он прогоняет тесты, читает diff, проверяет, что тесты не ослаблены, и выдаёт вердикт с обоснованием.

Скилл - это стабильная процедура, которую не нужно каждый раз объяснять заново.

  • Скилл проверки должен иметь понятное описание: по нему агент решает, когда его применять.
  • Вердикт - это артефакт: пройдено/не пройдено и доказательства, а не вежливое «выглядит хорошо».

  • Скилл включился без напоминания.
  • Отчёт содержит команды и вывод.
  • Слабая правка названа проваленной.
Режимы разрешений

Режим разрешает выполнять часть действий без вопросов. Курс перечисляет шесть режимов: ручной (чтение свободно, остальное спрашивает), accept edits (правки и простые файловые команды свободно), Plan (только исследование), Auto (всё принимается, но фоновый классификатор проверяет опасные действия), Don't ask (только предодобренное) и режим обхода подтверждений.

Выбор режима - решение о риске, которое принимается один раз, а не на каждом шаге.

Даже Auto не проверяет правильность кода, только опасность действий. Режим не заменяет проверку.

  • Цикл переключения режимов - Shift+Tab.
  • Чем автономнее режим, тем строже ваши проверки после.

Задание по мотивам курса: подобрать режим под задачу

Условие

  3. Проверьте на практике, что режим соответствует.

Критерии проверки:

  • Опасные правки в любом режиме требуют подтверждения, кроме обхода.
  • Вы понимаете, что Auto не гарантирует правильность.
Hooks в длинных сессиях

Claude Code запускает порядка тридцати событий хуков за сессию. Важнейшие: PreToolUse (перед вызовом инструмента), PostToolUse (после успешного вызова), Stop (агент хочет закончить), заметим, SubagentStop для субагентов.

PreToolUse - основной инструмент запретов. Stop позволяет не дать закончить, пока не выполнено условие, например не пройдены тесты.

Хуки - это код вне модели, поэтому поведение одинаково при любой модели и любом настроении сессии.

  • Хук должен быть быстрым: он стоит на пути каждого вызова.
  • Сообщения хуков пишите для модели, не только для себя.

Задание по мотивам курса: Stop-хук с условием

Условие

Запретите агенту заканчивать задачу без проверки.

  1. Сделайте Stop-хук, который запускает тесты или сборку и не даёт завершиться при ошибке.
  2. Спросите агента, что произошло, когда условие не выполнено.
  3. Проверьте, что при успешных тестах сессия завершается нормально.

Критерии проверки:

  • Сессия не завершается при падающих тестах.
  • При ошибке модель получает причину.
  • Обычная работа не замедлилась заметно.
Расписание и headless

Когда задача повторяется по одному и тому же запросу, её пора автоматизировать. Курс показывает спектр: облачные запланированные задачи и headless-режим с Agent SDK.

Запланированная задача - это сохранённый промпт, репозиторий и коннекторы, которые запускаются по cron, по HTTP-запросу или по событию GitHub. Ваша машина не участвует, инфраструктура на стороне Anthropic.

Headless - запуск Claude Code из вашего кода без интерфейса: удобно для CI, скриптов и собственных пайплайнов.

  • Начинайте с одной простой задачи (например, утренний отчёт по статусу), потом расширяйте.
  • Для автоматики заранее определите условие успеха: без него файлы не на что повесить.

  1. Опишите её как один промпт с условием успеха.
  2. Настройте запуск по расписанию (в облаке или через локальный скрипт с headless-режимом).

Критерии проверки:

  • Вы получаете отчёт о результате.

GitHub Actions и код-ревью

Pull request - лучшее место для рутины: там происходит ревью, туда приходят изменения.

Два подхода. Первый - управляемый сервис Code Review от Anthropic: администратор включает его, устанавливает приложение Claude для GitHub и выбирает режим срабатывания (при открытии PR, при каждом push или только по комментарию @claude review). Findings публикуются как inline-комментарии с уровнями важности.

Второй путь - свой workflow через Actions: больше контроля, больше настройки (ключи, права, проверки).

  • Ревью агента не заменяет ревью человеком: оно снимает рутину, а не ответственность.
  • Ограничьте права токена доступа для Actions.

Как проверить самостоятельный запуск

Чем меньше вы наблюдали, тем больше должны проверить. Короткую сессию можно просмотреть глазами, полностью автономный запуск в CI - нет.

Автономные запуски оставляйте в Auto, а не в обходе подтверждений: классификатор всё же отсекает опасные действия. Но он не судит о правильности кода, поэтому проверка остаётся на вас.

Начинайте проверку с diff, а не с резюме агента: резюме - это чужое мнение о работе.

  • Пропорция: меньше контроля по ходу, строже проверка после.
  • Команда /code-review проходит по изменениям и называет проблемы.

33.4.8. Introduction to agent skills

Что такое скиллы

Скилл - папка с инструкциями и ресурсами, которую Claude Code находит и применяет для конкретных задач. Основной файл - SKILL.md с именем и описанием в заголовке.

Claude выбирает скилл по описанию: сравнивает ваш запрос со списком доступных описаний и активирует подходящие.

Личные скиллы лежат в ~/.claude/skills (во всех проектах), проектные - в .claude/skills репозитория (доступны всем, кто его клонирует).

Скиллы загружаются по требованию: в отличие от CLAUDE.md, который попадает в каждый диалог. Если вы повторяете одно и то же объяснение - это кандидат в скилл.

  • Проектный скилл - часть документации проекта: он переносит знания вместе с кодом.
  • Описание - это условие срабатывания, поэтому оно важнее самих шагов.

  3. Положите в проект и убедитесь, что скилл срабатывает по запросу.

Метаданные (имя, описание) находятся в заголовке SKILL.md, ниже - инструкции.

При конфликте имен приоритет: организация, затем личный, затем проектный. Скиллы из плагинов имеют пространство имен и не конфликтуют.

Обновление - правка SKILL.md, удаление - удаление папки. Изменения подхватываются в текущей сессии.

  • Инструкция, имя, описание - минимум, который нужен.

Организация через пошаговое раскрытие: SKILL.md не длиннее 500 строк, а справочные материалы, скрипты и шаблоны - отдельными файлами, которые читаются по мере необходимости.

Скрипты не загружаются в контекст: токены расходует только их вывод.

33.4.10. Introduction to evals

Какую модель выбрать: сравнение по цифрам

Выбор модели обычно делают интуицией или по совету. Но модели отличаются по возможностям, скорости и цене, и разница измеряется.

Эвал - это набор случаев: вход, ожидаемый ответ и способ оценить ответ модели. Ожидаемые ответы пишутся до запуска моделей.

Аналогия из курса: лестница. Прежде чем смотреть на цену, узнайте высоту стены. Слишком короткая лестница бесполезна по любой цене.

Учебный пример курса - вымышленная инженерная консалтинговая фирма Meridian: 50 отчётов в месяц, промпт извлекает три поля (номер проекта, статус сроков, главный риск).

  • Сначала определите порог точности, затем сравнивайте модели на одних и тех же случаях.
  • Оценивайте не только точность, но и стоимость одного случая.

Задание по мотивам курса

Условие

  2. Запишите 10-15 реальных входов и занесите ожидаемые ответы вручную.
  3. Прогоните две-три модели на одних и тех же случаях и посчитайте точность и стоимость.

Критерии проверки:

  • Все модели проверены на одних и тех же случаях.

Спросите пять инженеров, какая модель лучше, и получите пять мнений. Эвал даёт число, а полезный эвал может начинаться очень малым.

У эвала три части: реалистичные входы, ожидаемый ответ для каждого и способ оценить ответ модели.

Оценка бывает трех видов. Кодовая проверка - сравнение с ожидаемым значением или наличие ключевой фразы: быстро, надёжно, масштабируется. LLM-судья - отдельная модель с рубрикой: для свободных ответов, где правильных формулировок много. Человек - выборочная ручная оценка для калибровки.

33.4.11. Introduction to Model Context Protocol

Зачем нужен MCP

MCP - слой коммуникации, который даёт Claude контекст и инструменты без написания интеграционного кода под каждый сервис.

Без MCP для работы с GitHub вы бы сами писали схемы и функции под все возможности. С MCP это делает специальный сервер GitHub, а ваше приложение подключается к нему.

Архитектура: клиент MCP (ваше приложение) соединяется с MCP-серверами, у которых есть инструменты, промпты и ресурсы. Каждый сервер - интерфейс к внешнему сервису.

  • MCP переносит определение и выполнение инструментов из вашего кода в сервер.
  • Для готового сервиса часто уже есть MCP-сервер - сначала поищите его.

  2. Проверьте, есть ли для него MCP-сервер.

33.4.12. Introduction to subagents

Что такое субагенты

Субагент - специализированный помощник, которому Claude Code передаёт задачу. Он работает в собственном окне контекста и возвращает в основной поток только краткое резюме.

Проблема, которую он решает: каждое чтение файла, поиск и вызов инструмента занимает место в основном контексте. При долгой сессии он переполняется и агент теряет нить.

Стартовый контекст субагента: системный промпт из вашего файла конфигурации и описание задачи, которое пишет родительский агент. Всё остальное остаётся в его отдельном транскрипте.

Компромисс: основной поток не видит, как субагент пришёл к выводу.

  • Есть встроенные субагенты: общий исполнитель для многошаговых задач, исследовательский - для разбора незнакомого кода.
  • Типичный пример: «какой сервис обрабатывает возвраты?» - вопрос, где нужен только ответ.

  2. Задайте тот же вопрос через субагента.
  3. Сравните объём и время.

  • Ответ по существу тот же.

Свой субагент - это markdown-файл с YAML-заголовком. Он задаёт имя, описание, системный промпт и набор инструментов.

Проще всего попросить Claude сам сгенерировать файл: «создай субагента code-reviewer в .claude/agents/, который проверяет код на ошибки и читаемость, только чтение».

Область действия: файл в .claude/agents/ - для текущего проекта, в ~/.claude/agents/ - для всех проектов.

При создании можно ограничить доступные инструменты - это лучший способ удержать ревьюера от правок.

  • Если папки субагентов не было при запуске Claude Code, перезапустите сессию.
  • Read-only субагент - безопасный вариант для первых опытов.

Имя и описание каждого субагента включаются в системный промпт основного агента - по ним он решает, кого запускать.

Описание играет вторую роль: по нему основной агент формулирует задачу для субагента. Общее описание даёт расплывчатое поручение, точное - поручение с конкретными файлами.

Пример: добавьте в описание «обязательно указывайте, какие файлы проверять», и основной агент начнёт передавать списки файлов.

Полезно задавать формат вывода: таблица, список с источниками, вердикт.

  • Хорошее описание отвечает: что делает и когда именно его вызывать.
  • Формат результата - часть описания, а не пожелание.

Классический случай - исследовательская задача: главному потоку нужен ответ, а не пути поиска.

  • Делегирование - это выбор, а не автоматическая оптимизация.
  • Свою работу ревьюером дайте субагенту с чистым контекстом.

33.4.13. Model Context Protocol: Advanced topics

Sampling: сервер просит у клиента модель

Sampling позволяет серверу обращаться к языковой модели через подключённый клиент: не сервер вызывает Claude, а просит клиента сделать это за него.

Из этого следуют два варианта: дать серверу свой API-ключ и свою логику оплаты, либо использовать sampling. Второй проще: клиент уже подключён к Claude, он делает вызов и возвращает результат.

Ответственность и расходы на генерацию текста остаются на стороне клиента, а сервер только формулирует запрос.

  • Sampling переворачивает традиционную схему HTTP: инициатор запроса - сервер.
  • Для этого нужен транспорт, в котором сервер может инициировать запрос.

Sampling на практике

Практика: сервер собирает данные, формирует промпт и отправляет запрос на генерацию клиенту. Клиент выполняет его и возвращает текст.

Сервер и клиент обмениваются сообщениями по уже открытому соединению.

  • Ошибку генерации сервер должен обрабатывать как обычную ошибку.
  • Длина и формат ответа задаются в запросе.

Roots: доступ к файлам

Roots дают MCP-серверу доступ к конкретным папкам на вашей машине. Это система разрешений плюс поиск.

Без roots агент не знает, где лежит файл: пользователь говорит «конвертируй biking.mp4», а сервер не может искать по всему диску. Заставлять пользователя писать полные пути - плохой вариант.

С roots агент получает список разрешённых каталогов, ищет внутри них и находит нужный файл.

  • Roots ограничивают сервер пределами проектных папок.
  • Пользователь управляет списком разрешённых каталогов.

StreamableHTTP

StreamableHTTP позволяет клиенту подключаться к удалённому серверу по HTTP: сервер может быть публичным и размещён в сети.

Важное предупреждение: настройки stateless_http и json_response по умолчанию выключены; их включение в некоторых сценариях разворачивания ломает прогресс, журналы и запросы от сервера.

Проблема в том, что обычный HTTP предполагает запросы только от клиента к серверу.

  • Если локально всё работает, а на HTTP - нет, проверьте эти два флага.
  • Для функциональности, где нужен запрос от сервера, нужен транспорт с долгим соединением.

StreamableHTTP подробнее

Часть возможностей MCP требует, чтобы запрос отправлял сервер (sampling, уведомления, журналы), а HTTP устроен наоборот.

Решения - долгие соединения: клиент открывает поток событий и получает ответные сообщения сервера.

Подключение: Initialize, ответ с идентификатором сессии, уведомление Initialized, затем обычная работа.

  • Идентификатор сессии связывает потоки запросов и событий.
  • Без потока событий запросы сервера к клиенту невозможны.

Состояние и масштабирование

Флаги stateless_http и json_response меняют поведение сервера при масштабировании и в эксплуатации.

При горизонтальном масштабировании запросы клиента попадают на разные экземпляры сервера, а клиенту нужны два соединения: поток событий и запросы POST. Если их обслуживают разные экземпляры, согласование становится сложным.

Stateless-режим решает часть проблем, но отключает возможности, где сервер должен инициировать запрос.

  • Выбирайте режим по требованиям, а не по удобству развертывания.
  • Сессии требуют привязки клиента к экземпляру или общего хранилища.

Инструменты, которые модель выбирает правильно

Симптомы: модель вызывает не тот инструмент, делает три вызова вместо одного, передаёт 0142 вместо MEG-2026-0142.

Причина почти всегда в определении инструмента: модель видит только описание, которое вы отправили, и результаты, которые вы вернули.

Переписав определения, Meridian на той же модели подняла балл с 14 до 26 из 30 тестовых вопросов.

  • Описание должно отвечать, когда вызывать инструмент, а не только что он делает.
  • Проверяйте выбор инструмента тестами, как и промпты.

Строгая схема

Обычно модель следует схеме, но ничто это не гарантирует: приходят строка "2" вместо числа 2, пропущенные поля.

Отсюда отказы вашего бэкенда на собственные вызовы модели.

Флаг strict: true заставляет вызов строго соответствовать схеме: схема компилируется в грамматику, и модель может писать только допустимые токены.

  • Включайте strict для инструментов, где ошибка типа дорога.
  • Полностью описывайте обязательные поля и допустимые значения.

Ваш цикл должен обработать каждый вызов и вернуть результат на каждый.

  • Не выполняйте вызовы последовательно в цикле, если они независимы.
  • Каждому запросу - ровно один ответ.

Снижение стоимости

Агент с инструментами отправляет всё заново при каждом запросе, и стоимость растёт с каждым вызовом.

Программное вызово инструментов и кэширование промптов срезают разную часть этой стоимости.

Пример из курса: один вопрос, 42 запроса, 1,1 млн входных токенов, 2,29 доллара в токенах.

  • Печатайте usage.input_tokens при каждом ответе, чтобы видеть, где расход.
  • Кэшируйте определения инструментов и системный промпт.
