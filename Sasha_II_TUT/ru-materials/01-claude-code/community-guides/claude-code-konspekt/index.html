Как устроен каждый блок

Сквозная формула, чтобы не тонуть в теории:

  • Правило - что делать, одной фразой.
  • Почему так - что ломается, если делать иначе. Без этого правило не приживается.
  • Как применить - конкретные шаги, команды, куда нажать.
  • Промпт - готовый текст для копирования в Claude. Кнопка справа сверху.

Про кавычки. Текст в кавычках с пометкой «дословно» - цитата из официальной документации Anthropic или материалов Academy в моём переводе, приведённая для точности. Всё остальное - мой пересказ. Ссылки на первоисточники в части 0 и в подвале.

Часть 1

База: как устроен агент и рабочий цикл

Курс Claude Code 101 целиком. Как агент думает, как его поставить, как с ним разговаривать и какой ритм работы Anthropic называет ядром всего обучения.

1.1Чем агент отличается от чата~7 мин▼

Claude в браузере - собеседник: ты копируешь ему текст, он отвечает текстом, ты копируешь ответ обратно. Claude Code - исполнитель: он живёт на твоём компьютере, сам открывает файлы, сам их меняет, сам запускает команды и сам проверяет, что получилось. Разница не в модели, модель та же. Разница в том, что у него есть руки.

Агентный цикл - три фазы по кругу

Это главная мысль первого раздела курса. Claude Code работает не одним ответом, а циклом:

1

Собрать контекст. Прочитать нужные файлы, посмотреть структуру папки, при необходимости выполнить команду и посмотреть на её вывод.

2

Сделать действие. Изменить файл, создать новый, запустить процесс.

3

Проверить результат. Перечитать, что вышло, запустить проверку, сравнить с задачей. Не сошлось - вернуться к шагу 1.

Круг повторяется, пока задача не закрыта. Отсюда практический вывод, который проходит через все четыре курса: дай агенту, чем проверить свою работу - и он закроет цикл сам. Не дашь - проверяющим становишься ты.

Правило
Дай Claude способ проверить себя - иначе проверяющим становишься ты

Почему так. Документация формулирует жёстко: «Claude останавливается, когда работа выглядит законченной. Без проверки, которую он может запустить, "выглядит законченной" - единственный доступный ему сигнал». Он честно не знает, что ошибся.

Как применить. В том же сообщении, где ставишь задачу, скажи, чем проверять: сверить с исходником, перечитать файл заново, запустить сборку, показать список изменений. И проси доказательство, а не слово «готово».

Что Claude Code видит, когда ты его запускаешь

Стоит знать точно, это вопрос осознанности:

  • Файлы твоей папки и всех вложенных в неё (другие места - только с твоего разрешения).
  • Твой терминал: любую команду, которую ты мог бы запустить сам.
  • Состояние git: текущая ветка, несохранённые правки, история.
  • Файл CLAUDE.md и авто-память (первые 200 строк или 25 КБ файла MEMORY.md).
  • Подключённые расширения: MCP-серверы, скиллы, сабагенты, связку с Chrome.
⚠️

Разговоры лежат на диске открытым текстом. Каждое сообщение, вызов инструмента и результат пишутся в файлы ~/.claude/projects/. Учитывай это, если работаешь с чувствительными данными.

Промпт: спросить Claude Code о нём самом
Объясни мне, как ты устроен и что умеешь, на примере моих задач: я работаю с текстами, таблицами, документами и файлами, я не программист.

Расскажи, какие твои функции реально пригодятся в такой работе, а какие мне не нужны. Приводи конкретные примеры, а не общие слова.
💡

Работает всегда: у Claude Code есть доступ к самой свежей документации о себе, независимо от установленной версии. Не помнишь, умеет ли он что-то - спроси его, а не ищи в интернете.

Курс отдельно снимает главный барьер: терминал не обязателен. Claude Code ставится в пять сред, движок везде один и тот же.

Правило
Ставь нативным установщиком - он сам обновляется

Почему так. Нативная установка обновляется в фоне. Homebrew, WinGet, apt, dnf и apk - нет, их надо обновлять руками. Поставишь не тем способом - через пару месяцев сидишь на старой версии без новых функций и без заплаток безопасности.

Как применить. Mac / Linux: curl -fsSL https://claude.ai/install.sh | bash. Windows PowerShell: irm https://claude.ai/install.ps1 | iex. Дождись надписи «Claude Code successfully installed!», потом проверь: claude --version.

🚫

Не ставь через sudo npm install -g. Прямое предупреждение документации: это ведёт к проблемам с правами и рискам безопасности. Если нужен npm - без sudo, и обновлять через npm install -g @anthropic-ai/claude-code@latest, а не npm update -g.

⚠️

Бесплатный тариф не подойдёт. Дословно: «The free Claude.ai plan does not include Claude Code access». Нужен Pro, Max, Team, Enterprise или аккаунт Console с API-кредитами.

Частые ошибки установки и что они значат▼
  • command not found: claude - установка прошла, но система не знает, где искать файл. Это не поломка. Установщик печатает решение в блоке Setup notes. Вручную для macOS: echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.zshrc, затем source ~/.zshrc. Обязательно открой новое окно терминала.
  • Посыпался HTML или syntax error near unexpected token '<' - по адресу установки вернулась веб-страница вместо скрипта. Если там написано «App unavailable in region» - Claude Code недоступен в твоей стране.
  • dyld: Symbol not found или built for Mac OS X 13.0 - macOS старее поддерживаемой. Минимум 13.0.
  • На 64-битной Windows пишет «does not support 32-bit Windows» - открыт PowerShell (x86). Закрой и открой пункт меню без «(x86)».
  • Не понимаешь, PowerShell у тебя или CMD - смотри начало строки: PS C:\...> это PowerShell, без PS - CMD. Команды у них разные.
Правило
Всегда запускай Claude изнутри той папки, с которой работаешь

Почему так. Claude видит файлы текущей папки и всех вложенных. Сессия привязана к директории. Запустишь в домашней папке - он будет искать твой проект вслепую.

Как применить. Сначала cd путь/к/папке, потом claude. Хитрость: набери cd, пробел, и перетащи папку мышкой в окно терминала - путь подставится сам.

Промпт: проверить, что всё встало правильно
Проверь моё окружение: какая у меня версия Claude Code, в какой папке я сейчас нахожусь, какие настройки подхватились и есть ли в них ошибки.

Если что-то настроено неправильно или чего-то не хватает - скажи прямо и предложи, как починить.

Ещё есть встроенная диагностика: команда claude doctor в терминале печатает состояние установки и настроек, не запуская сессию.

1.3Первый разговор: как формулировать задачи~12 мин▼

Это тот раздел курса, где закладывается разница между «ИИ мне не помогает» и рабочим инструментом.

Правило
Первый вопрос - на понимание, а не на изменение

Почему так. «Let Claude explore first» - дай ему сначала разобраться. Он читает файлы сам, вручную ничего прикреплять не надо. Правка без разведки бьёт мимо.

Как применить. Начни с «что это за папка», «как тут всё устроено», «какие файлы главные». Только потом проси менять.

Правило
Разговаривай как с коллегой, а не как с поисковой строкой

Почему так. Дословно: «Talk to Claude like you would a helpful colleague». И отдельный принцип - «Delegate, don't dictate»: дай контекст и направление, детали он разберёт сам. Люди либо пишут два слова, либо расписывают за него каждый шаг - плохо и то, и другое.

Как применить. Не «почини ошибку», а «после ввода неверного пароля пользователь видит пустой экран, смотри в папке авторизации, разберись и почини». Симптом и где искать - да. Какие файлы читать - не надо.

Правило
Сложную задачу нумеруй прямо в одном сообщении

Почему так. Отдельный приём документации. Claude удерживает многошаговую работу и идёт по списку, вместо того чтобы гадать, с чего начать.

Как применить. Пиши списком: 1) сделай то, 2) потом это, 3) в конце проверь так-то.

Правило
Не начинай заново, если ответ не тот - поправь следующей репликой

Почему так. «Это разговор. Когда первая попытка не та, ты не начинаешь сначала - ты уточняешь». Новый запуск стирает контекст, уточнение внутри сессии его сохраняет.

Как применить. Два способа вмешаться: Esc - остановить немедленно; либо просто напечатать поправку и нажать Enter - Claude прочитает её, как только закончит текущее действие, и скорректирует следующий шаг.

💡

Пока Claude работает, можно печатать дальше. Сообщение встанет в очередь, а не перебьёт его. Забрать из очереди обратно - Up с первой строки ввода.

⚠️

Ссылка на папку через @ даёт только список файлов, а не их содержимое. На этом обжигаются: думают, что отдали Claude всю папку, а отдали оглавление. Нужен текст - перечисляй файлы поимённо или проси прочитать.

💡

Многострочное сообщение: Enter отправляет. Чтобы перенести строку - \ и Enter, либо Ctrl+J (работает везде), либо Shift+Enter в современных терминалах. Длинный текст можно просто вставить целиком.

Промпт: знакомство с папкой, самый первый запрос
Осмотрись в этой папке и объясни простыми словами: что здесь лежит, из каких разделов состоит, какие файлы главные, а какие вспомогательные.

Не меняй ничего, просто расскажи структуру так, чтобы понял человек, который эту папку не открывал.
Промпт: разложить сваленные файлы по папкам
Посмотри, какие файлы лежат в корне этой папки. Для каждого скажи, что это по содержанию и в какую папку его логично положить.

Составь список «файл -> куда переложить» и покажи мне его. Ничего не перемещай и не удаляй, пока я не скажу «да, делай».
Промпт: разобрать незнакомую таблицу или выгрузку
Открой этот файл и объясни человеческим языком: что это за данные, какие колонки за что отвечают, сколько строк, за какой период и что в них бросается в глаза.

Если увидишь пустые места, дубли или странные значения - назови их отдельным списком.
✅

Claude Code работает в любой папке, не только с кодом. В документации это отдельный раздел: запусти его в папке с заметками, документами, расшифровками - он ищет, правит и переорганизует их так же, как код. Это ровно твой сценарий.

1.4Ядро курса: Explore → Plan → Code → Commit~15 мин▼

Anthropic называет этот цикл ядром всего курса 101: «повторяемый ритм, чтобы разбить задачу, дать Claude предложить подход, проверять работу по ходу и аккуратно её завершить». Для не-кодовых задач он работает буквально так же.

E

Explore - разведка. «Прочитай эти файлы и разберись, как сейчас устроено. Пока ничего не меняй.» Claude собирает картину.

P

Plan - план. «Составь план: что изменишь, в каком порядке, что может сломаться, как проверим.» Ты утверждаешь.

C

Code - исполнение. «Делай по плану.» Claude работает, ты смотришь по ходу и правишь курс, если надо.

C

Commit - фиксация. Сохранить результат: коммит в git, готовый файл, отчёт. Работа закрыта, к ней можно вернуться.

Плановый режим: техническая опора этого цикла

Чтобы фаза Plan была настоящей, есть отдельный режим: Claude читает файлы и предлагает план, но физически ничего не меняет на диске, пока ты не утвердишь.

  • Включить: Shift+Tab до надписи «plan mode on», либо запуск claude --permission-mode plan, либо команда /plan.
  • План можно отредактировать руками: когда Claude его показал, нажми Ctrl+G - план откроется в твоём текстовом редакторе. Выкинуть лишний пункт из плана проще, чем потом откатывать сделанное.
⚠️

Не включай плановый режим на мелочи. Прямое предупреждение: «Если изменение описывается одной фразой - пропусти план». Планирование окупается на многофайловых и незнакомых задачах, а на опечатке это лишний круг.

Промпт: сначала план, потом работа
Пока ничего не меняй. Прочитай [ФАЙЛЫ/ПАПКИ] и разберись, как там сейчас всё устроено.

Потом составь подробный план: какие файлы придётся изменить, в каком порядке, что может сломаться и как мы это проверим.

Покажи план мне на утверждение. Начнёшь делать только после моего «да».
Промпт: правка с обязательной проверкой в конце
Внеси такое изменение: [ЧТО НУЖНО].

После правки обязательно проверь результат: [ЧЕМ ПРОВЕРЯТЬ - перечитай файл и сверь с исходником / собери документ / запусти проверку].

Покажи мне, что именно ты запустил и что оно вернуло. Если проверка не прошла - чини и проверяй снова, пока не пройдёт. Не говори «готово» без доказательства.

Отладка в три хода

Документация разбирает починку ошибок именно так, и это переносится на любую поломку - хоть в скрипте, хоть в выгрузке, хоть в вёрстке письма:

1

Покажи ошибку и как её повторить. Не только текст ошибки, но и команду для воспроизведения, и стабильная она или плавающая. Без этого Claude чинит симптом, а не причину.

2

Проси варианты, а не правку. «Предложи 2-3 способа исправить с плюсами и минусами.» Ты сохраняешь право выбора.

3

Применяй выбранный. «Сделай второй вариант.»

Промпт: отладка по правилам Anthropic
У меня ошибка. Воспроизводится так: я запускаю [ЧТО ДЕЛАЮ], после чего вижу [ТЕКСТ ОШИБКИ]. Ошибка [стабильная / плавающая].

Не чини сразу. Сначала найди причину, а не симптом, и предложи 2-3 разных способа исправления с плюсами и минусами каждого.

Я выберу, и только после этого правь.

Рефакторинг: маленькими проверяемыми кусками

Правило документации: «делай переделку небольшими проверяемыми шагами» и обязательно проверяй в конце. Крупная переделка без проверки ломает то, что работало.

Промпт: аккуратная переделка старого материала
Найди в [ПАПКА/ФАЙЛ] всё устаревшее и дублирующееся: [ЧТО СЧИТАТЬ УСТАРЕВШИМ].

Составь список находок, но пока ничего не правь.

Дальше пойдём маленькими шагами: я укажу первый пункт, ты его переделаешь, сохранив прежний смысл, покажешь мне разницу до и после, и только потом мы возьмём следующий.

Объясняй на каждом шаге, что мы от изменения выигрываем и что теряем.

Работа с картинками

Три способа вставить: перетащить файл в окно, вставить из буфера (Ctrl+V, на Windows и WSL Alt+V, в iTerm2 Cmd+V), или написать путь к файлу. Четыре типовых вопроса: что на картинке, разбери элементы, вот скриншот ошибки - в чём причина, свёрстай по этому макету.

✅

Приём из лучших практик: второй Claude как рецензент. Тот, кто делал, - плохой судья того, что сделал. Открой вторую сессию и дай ей проверить результат первой: «свежий контекст судит честнее, потому что не привязан к тому, что сам только что написал».

⚠️

Но рецензенту ставь рамки. Прямое предупреждение: «Рецензент, которого попросили найти пробелы, почти всегда что-нибудь найдёт, даже если работа хорошая - потому что его об этом попросили. Гонка за каждой находкой ведёт к переусложнению». Добавляй в запрос: «отмечай только то, что влияет на корректность или на заявленные требования, стилистические придирки не пиши».

Промпт: второй Claude как рецензент
Проверь изменения в @путь/к/файлу против того, что мы планировали в [ФАЙЛ С ПЛАНОМ или описание задачи].

Проверь, что каждое требование выполнено, что пограничные случаи учтены и что ничего лишнего сверх задачи не изменилось.

Отмечай только то, что влияет на корректность или на заявленные требования. Стилистические придирки не пиши.
Промпт: интервью перед большой задачей
Я хочу сделать [КОРОТКОЕ ОПИСАНИЕ]. Возьми у меня подробное интервью.

Спрашивай про реализацию, про то, как это увидит человек со стороны, про пограничные случаи, риски и компромиссы. Очевидное не спрашивай - копай в те трудные места, о которых я мог не подумать.

Продолжай интервью, пока не покроем всё, а потом запиши полную спецификацию в файл SPEC.md.
💡

Дальше по этой спецификации работают в новой сессии с чистым контекстом: интервью съедает много контекста, а исполнителю нужен только итоговый документ.

1.5Контекст: главный расходник, за которым надо следить~12 мин▼

Окно контекста - это рабочая память одного разговора. Ключевой факт, который меняет привычки: Claude Code отправляет весь разговор целиком с каждым новым сообщением. Утром разбирал ученика, вечером в том же окне пишешь пост - разбор ученика всё ещё едет в каждом запросе. Это и деньги, и качество: старый контекст отвлекает и вытесняет нужное.

Правило
Сменил тему - /clear. Та же тема, но разговор разбух - /compact

Почему так. В документации есть имя для антипаттерна: «сессия-помойка» (kitchen sink session) - начал одно, спросил про другое, вернулся к первому. Важная деталь про деньги: /clear не стоит ничего, а /compact - это сам по себе большой запрос, он читает весь разговор, чтобы его пересказать. Вызывать /compact «для чистоты» между разными задачами - выбрасывать деньги.

Как применить. Закончил задачу - /clear. Если разговор может пригодиться, сначала дай ему имя: /rename разбор-ученика. Или прямо при очистке: /clear разбор-ученика - это назовёт уходящий разговор, найдёшь его потом в /resume.

Правило
Всегда давай /compact фокус, никогда не запускай его голым

Почему так. Без инструкции резюме составляется на глазок - Claude сам угадывает, что важно. А всё, что не попало в резюме, для него перестаёт существовать: полные выводы команд и промежуточные рассуждения исчезают навсегда.

Как применить. Пиши инструкцию сразу после команды: /compact сохрани список изменённых файлов, финальный текст поста и все мои правки дословно.

💡

Лучший момент для /compact - естественная пауза между этапами работы, а не когда автосжатие сработает само посреди сложного шага.

Почему так. Сабагент работает в своём отдельном окне. Он может прочитать хоть двадцать файлов - к тебе вернётся только выжимка. В примере из документации сабагент прочитал 6100 токенов, а в главный контекст вернулось 420.

Как применить. Скажи прямо: «отправь сабагента изучить все файлы в этой папке и вернуть только выводы». Или командой /subtask.

⚠️

Не меняй модель и уровень усилия посреди задачи. Кеш привязан к модели и к уровню усилия. Переключение означает, что следующий запрос перечитает весь разговор без единого попадания в кеш - медленно и дорого. Выбирай в начале сессии.

Промпт: что съело мой контекст и что делать
Выполни команду /context и покажи мне результат. Потом объясни простыми словами, без технического жаргона:

1. Сколько процентов окна контекста уже занято.
2. Что именно занимает больше всего места - назови топ-3 позиции с числами.
3. Что из этого можно безболезненно убрать прямо сейчас.
4. Что мне выгоднее сделать: /clear (стереть всё и начать заново) или /compact (сжать разговор и продолжить ту же работу). Объясни, почему именно этот вариант.

Если предлагаешь /compact - сразу напиши мне готовую строку с фокусом, которую я скопирую и вставлю.
Промпт: правильно сжаться перед сменой этапа
Мы подошли к пределу контекста, но работа не закончена. Сделай так:

1. Сначала выпиши списком, что ОБЯЗАТЕЛЬНО должно пережить сжатие: какие решения мы приняли, какие файлы изменили, какие мои правки и формулировки нужно сохранить дословно, что осталось сделать.
2. На основе этого списка составь готовую команду вида /compact <инструкция>, чтобы я её скопировал и вставил.
3. Отдельно предупреди, что после сжатия потеряется навсегда - чтобы я решил, не нужно ли это сначала сохранить в файл.

Сам /compact не запускай, я сделаю это вручную.
🚫

После двух неудачных исправлений подряд - не спорь в третий раз. Прямая цитата: «Чистая сессия с хорошим промптом почти всегда обыгрывает длинную сессию с накопленными исправлениями». Делай /clear и пиши задачу заново, вложив в неё то, что понял из провалов: «Сделай X. Важно: не делай Y и не используй Z, я это уже пробовал».

1.6Откат: страховка, которая уже включена~10 мин▼

Многие боятся давать агенту править файлы, потому что не знают: откат встроен и работает по умолчанию. Перед каждым твоим сообщением Claude Code сам делает снимок состояния файлов. Специально ничего сохранять не надо.

Правило
Откат - Esc Esc при пустом поле ввода, либо команда /rewind

Почему так. Если в поле ввода есть текст, двойной Esc сработает иначе - сотрёт черновик, а меню не откроется. Люди жмут, «ничего не происходит», и решают, что функция сломана. Стёртый черновик, кстати, возвращается стрелкой Up.

Как применить. Очисти поле ввода и жми Esc Esc. Откроется список всех твоих сообщений сессии - выбирай точку возврата.

Пять вариантов в меню отката

ПунктЧто делает
Restore code and conversationВернуть и файлы, и переписку
Restore conversationВернуть переписку, файлы оставить как есть
Restore codeВернуть файлы, переписку оставить
Summarize from hereСжать всё после этой точки, ранние инструкции сохранить целиком
Summarize up to hereСжать всё до этой точки, свежие сообщения оставить
✅

Главный смысл отката - не вернуться, а переспросить иначе. После отката переписки твой прежний запрос сам возвращается в поле ввода. Отредактируй формулировку и отправь заново - Claude пойдёт другим путём.

💡

Сжатием можно управлять: подведи стрелками к пункту Summarize (не нажимай цифру!), появится строка «add context (optional)» - впиши туда, что обязательно сохранить, и жми Enter. Выберешь цифрой - сожмётся сразу, без твоих указаний.

Четыре дыры в страховке - знать обязательно

🚫

1. Правки через команды терминала не откатываются. Отслеживаются только изменения через инструменты редактирования Claude. Команды rm, mv, cp - мимо. А удаление и перемещение файлов Claude делает именно командами. Вывод: не разрешай удалять и перемещать файлы командами без подтверждения. Здесь страховка только git или своя копия папки.

⚠️

2. Правки сабагентов обычно не откатываются. Можно решить, что откат вернул всё, а часть правок останется. Их возвращают через git.

⚠️

3. Действия наружу не откатываются в принципе. Отправленный пост, письмо, запись в Notion, деплой - чекпоинт не вернёт. Этим управляют до факта, режимом разрешений.

⚠️

4. Файлы-ярлыки откат пропускает. Покажет предупреждение «Restored the code, but skipped N files». Не заметишь - будешь думать, что откатил всё. Хочешь видеть, что именно пропущено - включи /debug до отката, список ляжет в ~/.claude/debug/.

Правило
Чекпоинты - это «отменить последние полчаса», а не система версий

Почему так. Дословный заголовок документации: «Не замена контролю версий». Хранится только 100 последних точек сессии, живут 30 дней. В сессии из 300 сообщений к пятидесятому уже не вернёшься.

Как применить. Ближняя дистанция - чекпоинт. Долгая история, важные версии, многодневная работа - git-коммиты или копии папки.

✅

Случайно сделал /clear и пожалел? Не закрывай окно. Нажми Esc Esc - в самом верху списка появится строка /resume <session-id> (previous session). Работает только в том же запущенном процессе.

💡

Откатить или сохранить оба варианта? /rewind меняет текущую сессию. /branch имя создаёт копию разговора и переключает в неё, оригинал остаётся целым - так пробуют рискованный подход, не теряя рабочий.

1.7Сессии: продолжить вчерашнее, назвать, разветвить~8 мин▼

Ключевой факт, на котором спотыкаются все: каждая новая сессия - чистый лист. Claude не помнит вчера. Единственное, что переезжает между сессиями, - файл CLAUDE.md и авто-память.

Правило
Не переобъясняй вчерашний контекст - продолжай прошлый разговор

Почему так. Claude Code сохраняет каждый разговор локально. Пересказывать вчерашнее заново - трата времени и токенов, и пересказ всегда беднее оригинала.

Как применить. claude --continue (или -c) - продолжить самый свежий разговор в этой папке. claude --resume (или -r) - выбрать из списка. /resume - переключиться, не выходя из текущей сессии.

Правило
Давай сессиям имена и относись к ним как к веткам работы

Почему так. Прямой совет из лучших практик: «называй сессии через /rename и относись к ним как к веткам: у каждого направления работы свой постоянный контекст». Без имён в списке будут безликие строки.

Как применить. На старте: claude -n имя-задачи. Внутри: /rename имя-задачи. Возврат: claude --resume имя-задачи.

Что не восстанавливается при возобновлении - важные тонкости▼
  • Флаги надо передавать заново: --mcp-config, --settings, --plugin-dir, --fallback-model, --add-dir. Обычные файлы настроек перечитываются сами.
  • Режим разрешений восстанавливается не всегда. Через терминал - да, но bypassPermissions и plan не восстанавливаются никогда. При выборе из списка и через /resume внутри сессии сохранённый режим не восстанавливается вовсе.
  • Сессии из claude -p не попадают в список и не подхватываются через --continue. Только по идентификатору: claude --resume <id>.
  • На Pro и Max при возобновлении сессии, которая простояла больше часа и весит свыше 100 000 токенов, появится выбор: свернуть в выжимку или загрузить целиком. Кеш к этому моменту уже истёк, так что первый запрос всё равно обработает всю историю.
  • Не возобновляй одну сессию в двух терминалах без ветвления - сообщения перемешаются в одну стенограмму.
💡

Выгрузка разговора: команда /export - в буфер или файлом. Не лезь в служебные файлы ~/.claude/projects/ напрямую: их формат внутренний и меняется между версиями, скрипты на них ломаются на любом релизе.

Промпт: восстановить картину после перерыва
Напомни мне коротко: на чём мы остановились в этой сессии, что уже сделано, что осталось и какой был следующий шаг.

Ничего не меняй, просто восстанови картину.

Перед этим в терминале: claude --continue, либо claude --resume и выбор сессии из списка.

Если непонятно, что именно подвело - сначала улучши сам запрос или правила в CLAUDE.md, и только потом крути рычаги.

Лестница «think → think hard → think harder → ultrathink» устарела. Документация говорит однозначно: фразы «think», «think hard», «think more» Claude Code пропускает как обычный текст промпта. Все курсы и статьи, которые учат этой лестнице, отстали от жизни. Работает только ultrathink.

Уровни усилия

Пять уровней: low, medium, high, xhigh, max. По умолчанию уже high, и документация прямо советует: «для большинства задач используйте уровень по умолчанию».

  • /effort без аргументов - откроется ползунок. /effort status - что стоит сейчас.
  • max склонен к переусложнению - дословно «prone to overthinking», даёт убывающую отдачу. Его советуют протестировать до постоянного применения.
  • max держится только на текущую сессию и слетает после перезапуска - защита от того, чтобы случайно не оставить самый дорогой режим навсегда. Остальные уровни запоминаются.
  • Один и тот же уровень на разных моделях - не одинаковое количество работы: шкала откалибрована под каждую модель отдельно.
⚠️

За размышления платишь всегда, даже когда они свёрнуты и ты их не видишь: «You are charged for all thinking tokens generated, even when collapsed or redacted». Посмотреть сами мысли - Ctrl+O (подробный режим, рассуждения серым курсивом).

Окно на 1 миллион токенов и запасные модели▼

1M контекст. Включается суффиксом: /model opus[1m], /model sonnet[1m]. Наценки за токены нет, но больше контекста = больше токенов в каждом запросе = быстрее расходуется лимит. На Max, Team и Enterprise Opus с 1М включён в подписку; на Pro требует usage credits.

Запасные модели. Чтобы работа не вставала при перегрузке: claude --fallback-model sonnet,haiku. Переключение действует только на текущий ход. Ошибки входа, оплаты и лимитов переключение не вызывают.

Если Claude сам сменил модель - обычно сработал классификатор безопасности по темам кибербезопасности или биологии. Бывает даже на первом запросе сессии, потому что он несёт содержимое CLAUDE.md и статус git. Документация подчёркивает: «это ожидаемая маршрутизация, а не пометка на аккаунте».

Настройка под себя: память, правила, режимы

Раздел Configure Claude из курса in Action плюс четвёртый раздел курса 101. Здесь Claude Code перестаёт быть универсальным и становится твоим. Главный урок курса называется «A CLAUDE.md That Follows» - файл правил, которому Claude действительно следует.

2.1CLAUDE.md: память проекта, которая работает~20 мин▼

Памяти две, и их постоянно путают:

Формулировка решает, куда ляжет. Скажешь «запомни, что...» - уйдёт в автопамять. Скажешь «добавь это в CLAUDE.md» - ляжет в файл правил. Это самая частая причина «я же просил запомнить, а он забыл».

Правило
CLAUDE.md - это контекст, а не закон

Почему так. Дословно: «Claude относится к нему как к контексту, а не как к принудительной конфигурации... он читает его и старается следовать, но строгого соблюдения не гарантируется». Технически файл приезжает пользовательским сообщением после системного промпта, а не частью системного промпта.

Как применить. Если действие обязано выполняться всегда и без исключений - это не текст в CLAUDE.md, а хук (раздел 2.4). Документация прямо: «чтобы заблокировать действие независимо от того, что решит Claude, используй PreToolUse-хук».

Файлы склеиваются в один текст, а не перебивают друг друга. Это отличается от настроек, где младший файл побеждает старший. Здесь всё складывается сверху вниз по дереву папок, поэтому противоречия между файлами не разрешаются автоматически - дословно: «если два правила противоречат друг другу, Claude может выбрать одно произвольно». Периодически вычищай.

Правило
Держи CLAUDE.md короче 200 строк

Почему так. Он грузится в контекст в начале каждого разговора, даже когда ты занимаешься совсем другим. И главное - раздутый файл не усиливает правила, а ослабляет их: «Bloated CLAUDE.md files cause Claude to ignore your actual instructions!»

Как применить. Прогони каждую строку через вопрос из документации: «Если это удалить, Claude начнёт ошибаться?» Нет - вырезай. Проверить объём: /context. Автоматически подрезать: /doctor.

Правило
Пиши конкретно и проверяемо, а не общими словами

Почему так. Размытая формулировка выполняется нестабильно. Документация прямо противопоставляет пары.

Как применить. «Черновик поста класть в sessions/active/<сессия>/post.md» вместо «складывать файлы аккуратно». «Перед публикацией прогнать проверку X» вместо «проверяй работу». Структурируй заголовками и списками: «Claude сканирует структуру так же, как читатель - организованные разделы понятнее плотных абзацев».

Если Claude упорно игнорирует одно правило - добавь IMPORTANT ровно к этой одной строке. Дословно: «Если выделить много строк, ни одна не будет выделяться». А если хочется выделить пять - значит, файл слишком длинный и правило тонет в шуме. Сначала сокращай.

Диагностика от Anthropic: если Claude задаёт вопросы, ответы на которые есть в CLAUDE.md - формулировка двусмысленная, а не он невнимательный.

Начинай не с чистого листа

Команда /init сама изучит проект и составит стартовый CLAUDE.md. Если файл уже есть - не затрёт, а предложит улучшения. Есть расширенный режим: переменная CLAUDE_CODE_NEW_INIT=1 включает интерактивный сценарий - Claude спросит, что настроить (CLAUDE.md, скиллы, хуки), изучит проект сабагентом, задаст уточняющие вопросы и покажет план до записи файлов.

Промпт: собрать CLAUDE.md через интервью
Создай в этой папке файл CLAUDE.md и запиши в него мои постоянные правила работы, чтобы ты читал их в начале каждой сессии.

Сначала задай мне уточняющие вопросы: как я хочу, чтобы ты со мной разговаривал, что тебе нельзя трогать без спроса, какой у нас формат файлов и куда что складывать.

Держись правил Anthropic для этого файла: короче 200 строк, конкретные проверяемые формулировки вместо общих слов, заголовки и списки вместо абзацев. Не пиши туда то, что ты и так поймёшь, прочитав файлы.

Потом покажи готовый черновик до сохранения.
Промпт: аудит раздутого CLAUDE.md
Прочитай мой CLAUDE.md и проверь его на раздутость. В документации Claude Code сказано держать этот файл короче 200 строк: он грузится в контекст в начале КАЖДОГО разговора, и раздутый файл заставляет тебя игнорировать половину инструкций.

Пройди по каждому блоку и задай вопрос: «Если это удалить, Claude начнёт ошибаться?»

Выдай три списка:
1. ОСТАВИТЬ - без этого сломается.
2. ВЫНЕСТИ В СКИЛЛ - узкие инструкции, нужные редко, должны грузиться по требованию. Для каждой скажи, в какой скилл.
3. УДАЛИТЬ - то, что ты и так делаешь правильно, или что выводится из самих файлов.

Посчитай, сколько строк сейчас и сколько останется. Ничего не удаляй сам - сначала покажи план.
Продвинутое: правила по папкам, импорты, скрытые комментарии▼

Правила по темам. Когда правил стало много - раскладывай .md файлы в .claude/rules/, по одному на тему. Личные правила для всех проектов - в ~/.claude/rules/, они грузятся раньше проектных, то есть проектные весомее.

Правило, привязанное к файлам. Главный способ не раздувать постоянный контекст: в шапке файла правила укажи paths: со списком шаблонов - и правило подгрузится только когда Claude откроет подходящий файл. Шаблоны: **/*.ts, src/**/*, *.md.

Импорты через @путь. Работают прямо в тексте CLAUDE.md, максимум 4 прыжка вглубь. Важно: импорт помогает организовать, но не экономит контекст - импортированные файлы грузятся при старте. Чтобы упомянуть путь и не импортировать - оберни в обратные кавычки.

Комментарии для себя. HTML-комментарии <!-- заметка --> вырезаются до передачи в контекст. Пиши в них, зачем ввёл правило - Claude их не увидит, контекст не потратится.

Что переживает сжатие контекста. Проектный корневой CLAUDE.md и автопамять подгружаются с диска заново. Вложенные CLAUDE.md и правила с paths вернутся только когда Claude снова откроет подходящий файл. Вывод документации: «инструкции, которые должны пережить сжатие, добавляй в CLAUDE.md».

Автопамять: что Claude пишет о тебе сам▼

Включена по умолчанию. Четыре типа записей: user (твоя роль, экспертиза, предпочтения), feedback (твои поправки и подтверждённые подходы), project (текущая работа, сроки, решения, которые не выводятся из файлов), reference (где искать информацию снаружи проекта).

Не пишет: то, что выводится из самого проекта, и то, что уже есть в твоих CLAUDE.md.

Лежит в ~/.claude/projects/<проект>/memory/, привязана к репозиторию, а не к папке - все рабочие копии делят одну память. Живёт только на этой машине, между компьютерами не синхронизируется.

Это обычные markdown-файлы: открывай через /memory, правь и удаляй руками. Запомнил ерунду - просто отредактируй.

Выключить: тумблер в /memory, либо {"autoMemoryEnabled": false} в настройках проекта, либо переменная CLAUDE_CODE_DISABLE_AUTO_MEMORY=1.

2.2Режимы разрешений: сколько свободы давать агенту~15 мин▼

Отдельный урок курса in Action. Режим - это единственная ручка, которой ты регулируешь уровень своего контроля. Переключается по Shift+Tab, текущий виден в строке состояния внизу.

РежимМетка внизуЧто делает
default / Manual⏸ manual mode onСпрашивает перед правкой файлов и командами. Полный контроль
auto⏵⏵ auto mode onДействия проверяет модель-классификатор вместо тебя
acceptEdits⏵⏵ accept edits onПравит файлы и делает базовые файловые команды без вопросов, остальное спрашивает

Правило
Auto mode - это не «отключить безопасность», а «заменить тебя вторым проверяющим»

Почему так. Люди путают его с bypassPermissions - и либо боятся, либо ждут полной защиты. Документация прямо: «Auto mode снижает количество запросов, но не гарантирует безопасность. Используй его для задач, где ты доверяешь общему направлению, а не как замену проверке на чувствительных операциях». А bypassPermissions вообще «не даёт никакой защиты от подсунутых инструкций и непреднамеренных действий».

Как применить. Обычная работа - auto. Чужие персональные данные, деньги, публикация наружу - переключись Shift+Tab в Manual и смотри каждый шаг. bypassPermissions - только внутри контейнера или виртуальной машины.

⚠️

На Pro, Max и Team новая сессия сама стартует в auto mode. Это встроенный дефолт 2026 года, а не твоя настройка. Не зная этого, легко решить, что Claude «стал непослушным» и перестал спрашивать. Вернуть старое поведение навсегда: {"permissions": {"defaultMode": "default"}} в ~/.claude/settings.json.

🚫

Тихая поломка, на которой все спотыкаются: значение "auto" не работает из настроек проекта - только из личного ~/.claude/settings.json. Пропишешь в папке проекта - сессия молча стартует в Manual, без единой ошибки. Причина в безопасности: иначе любой скачанный проект включал бы себе автономный режим сам.

Что не одобрится автоматически ни в одном режиме

Встроенный предохранитель против ошибки модели. Даже bypassPermissions это не проходит:

  • Инструменты под явным правилом ask.
  • Инструменты, требующие участия человека.
  • Удаления rm и rmdir по критическому пути - корень, домашняя папка, рабочая папка и её родители. Дословно: «никакое allow-правило и никакой хук не одобрят такое удаление».
✅

Спрятать удаление внутрь подстановки бесполезно: «сокрытие удаления внутри $(...), обратных кавычек или <(...) не пропускает проверку». Проверено на уровне разбора команды.

💡

Защищённые пути (.git, .claude, .zshrc и подобные) никогда не одобряются автоматически, и allow-правила на них не действуют: проверка безопасности выполняется раньше, чем читаются твои разрешения.

Граница словами в чате - работает, но ненадёжно

Правило
Разовое ограничение - словами. Постоянное - только правилом в настройках

Почему так. Классификатор считает твою фразу сигналом блокировки: скажешь «не публикуй, пока я не проверю» - совпадающие действия блокируются, даже если правила их разрешали. Но границы не сохраняются как правила: классификатор перечитывает их из переписки каждый раз, и при сжатии контекста фраза может исчезнуть.

Как применить. Постоянное «никогда» - в permissions.deny. Постоянное «всегда спрашивай» - в permissions.ask. И запомни: «собственное суждение Claude о том, что условие выполнено, границу не снимает» - снять можешь только ты новым сообщением.

💡

Общая просьба не считается разрешением. Дословно: «попросить Claude "прибраться в репозитории" не даёт права на force push, а попросить "сделай force push этой ветки" - даёт». Хочешь действие - назови его прямо.

✅

Классификатор читает твой CLAUDE.md. Правило «никогда не публикуй без команды», написанное в файле, направляет одновременно и Claude, и проверяющего. При этом результаты работы инструментов классификатор не видит - подсунутые в файл или на веб-страницу команды им не управляют.

⚠️

Auto mode сам ставится на паузу после 3 блокировок подряд или 20 за сессию - и снова начинает спрашивать. Пороги не настраиваются. Если режим «сломался» - ты просто упёрся в лимит.

2.3Правила разрешений: разрешить, спросить, запретить~15 мин▼

Три списка в настройках: allow (делай без вопросов), ask (всегда спрашивай), deny (нельзя никогда). Формат правила: Инструмент или Инструмент(уточнение).

Правило
Запрет побеждает всё и отовсюду - из него нельзя сделать исключение

Почему так. Обычные настройки работают по старшинству уровней, но для разрешений действует отдельное правило: если инструмент запрещён на любом уровне, никакой другой уровень его не разрешит. Запрет организации не отменяется флагом командной строки, твой личный запрет блокирует разрешение из проекта.

Как применить. Свои жёсткие «никогда» (например, запрет читать файлы с секретами) клади в личный ~/.claude/settings.json - они будут работать во всех проектах, и их не перебьёт ни один проектный файл. И пиши запреты узко: «всё нельзя, кроме одного» через широкий deny не собрать.

Пять ловушек синтаксиса, на которых ошибаются все

Ловушка 1
Звёздочку ставь после подкоманды, а не до неё

Почему так. Всё, что стоит до первой звёздочки, сопоставляется буквально - именно эти слова и ограничивают правило. Bash(git log *) разрешает только git log. А Bash(git *) разрешает любую git-команду, включая публикацию и запуск произвольной программы через хитрый флаг.

Как применить. Правильно: Bash(npm run *), Bash(git commit *). Опасно: Bash(git * main), Bash(* --version). Claude Code даже показывает предупреждение при старте, если звёздочка стоит раньше подкоманды.

Ловушка 2
Пробел перед конечной звёздочкой - часть правила

Почему так. Bash(ls *) требует пробел после ls, поэтому под него не попадает команда lsof. А Bash(ls*) без пробела - попадает. Незаметная дыра.

Как применить. Всегда ставь пробел. Бонус: конечная звёздочка с пробелом ловит и голую команду - Bash(git log *) сработает и на просто git log.

Ловушка 3
Для файлов работают только Read(...) и Edit(...)

Почему так. Claude Code сверяет файловые разрешения только с правилами Read и Edit. Напишешь Write(docs/**) - правило примут, но оно никогда не применится, а при старте будет предупреждение.

Как применить. Пиши Edit(docs/**) вместо Write, MultiEdit и NotebookEdit с путями. Пиши Read(docs/**) вместо Glob. Правило без пути (просто Write) работает - оно бьёт по инструменту целиком.

Ловушка 4
Одна косая черта в начале - это не корень диска

Почему так. Самая частая ошибка в путях. /path привязывается к источнику настроек, а не к корню файловой системы. Правило Read(/secrets/**) в личном ~/.claude/settings.json заблокирует ~/.claude/secrets/**, а вовсе не папку в проекте.

Как применить. Четыре формы: //path - абсолютный от корня диска; ~/path - от домашней папки; /path - от источника настроек; path или ./path - от текущей папки. Для личных настроек, работающих во всех проектах, - // или ~/.

Ловушка 5
Запускалки окружения открывают дыру шириной в грузовик

Почему так. Claude Code снимает фиксированный набор безобидных обёрток (timeout, nice, nohup и подобные), чтобы правила срабатывали. Но в этом списке нет запускалок вроде npx, docker exec, devbox run. Правило Bash(devbox run *) разрешит всё, что идёт после run, включая удаление файлов.

Как применить. Пиши правило целиком, по одному на каждую внутреннюю команду: Bash(devbox run npm test).

✅

Составные команды разбираются по частям. Правило Bash(safe-cmd *) не даст выполнить safe-cmd && other-cmd - защита от «подклеивания» опасной команды к разрешённой. Распознаются &&, ||, ;, |, & и перевод строки.

💡

Часть команд выполняется без вопроса в любом режиме - встроенный ненастраиваемый набор «только чтение»: ls, cat, echo, pwd, head, tail, grep, find, wc, which, diff, stat, du, cd и читающие формы git. Поэтому Claude свободно осматривается даже в ручном режиме. Хочешь, чтобы и это спрашивало - только правилом ask или deny.

💡

Перенаправление вывода (>, >>) проверяется как запись в файл, отдельно от самой команды. Цель, начинающаяся с ~ или содержащая маску, всегда требует подтверждения.

💡

Запрет на чтение закрывает и запись по тому же пути - но не правку блокнотов Jupyter. Для путей, которые никто не должен менять, добавляй оба: deny: ["Read(./секреты/**)", "Edit(./секреты/**)"].

✅

Ссылкой ограничение не обойти. Разрешение срабатывает, только если совпали оба пути - и сама ссылка, и то, куда она ведёт. Запрет срабатывает, если совпал хоть один.

Промпт: настроить защиту от катастроф
Настрой мне правила безопасности в моих личных настройках ~/.claude/settings.json, чтобы они действовали во всех проектах.

ЗАПРЕТИ (permissions.deny):

Учти правила синтаксиса из документации: звёздочка только ПОСЛЕ подкоманды и с пробелом перед ней; для файлов работают только Read(...) и Edit(...), а Write с путём молча не применяется; одинарный слеш в начале пути считается от источника настроек, а не от корня диска.

Покажи мне готовый файл и объясни каждую строку простыми словами. Потом проверь командой /permissions, что правила подхватились.

2.4Хуки: правила, которые нельзя не выполнить~20 мин▼

Урок Hooks есть в обоих курсах - и в 101, и в in Action. Это самый недооценённый механизм, потому что решает проблему, с которой все мучаются: Claude иногда не делает то, что написано в правилах.

Правило
Хук - там, где нужна гарантия. CLAUDE.md - там, где достаточно пожелания

Почему так. CLAUDE.md - просьба к модели: её можно не выполнить, а после сжатия контекста ещё и забыть. Хук выполняется программой Claude Code, а не моделью, поэтому срабатывает всегда. В документации это называется детерминированным контролем: «определённые действия происходят всегда, а не когда модель решит их выполнить».

Как применить. Переноси в хуки: «никогда не читай файлы с секретами», «всегда логируй команды», «уведоми, когда ждёшь моего ответа», «не дай завершить работу, пока не прошла проверка». Оставляй в CLAUDE.md: «пиши в моём тоне» - хук не умеет судить о стиле.

Три уровня вложенности - структура, которую надо запомнить

Ошибка вложенности - и хук просто не появится, без единого сообщения об ошибке:

Структура конфигурации
"hooks": {
  "ИмяСобытия": [
    {
      "matcher": "фильтр",
      "hooks": [
        { "type": "command", "command": "что запустить" }
      ]
    }
  ]
}

Слово hooks встречается дважды: внешнее - объект со всеми событиями, внутреннее - массив обработчиков внутри группы.

🚫

Добавляешь хук туда, где блок уже есть - дописывай событие соседним ключом, не заменяй объект целиком. Все события живут внутри одного объекта hooks. Вставишь новый поверх старого - все прежние хуки исчезнут.

Пять ловушек, из-за которых хук молча не работает

Ловушка 1
Блокирует только код выхода 2. Код 1 не блокирует

Почему так. Привычное по Unix «код 1 = ошибка» здесь означает всего лишь неблокирующую ошибку: действие пройдёт. Политика, написанная через exit 1, молча не работает.

Как применить. Запрет: причина в stderr (echo "текст" >&2) и exit 2. Промолчать: exit 0.

Ловушка 2
В stdout должен быть только JSON и ничего кроме

Почему так. Claude Code разбирает вывод как JSON, только если текст начинается с { и заканчивается }. Любое лишнее приветствие из твоего профиля оболочки склеивается с JSON - и всё решение молча игнорируется.

Как применить. В ~/.zshrc оберни все echo в проверку интерактивности. JSON собирай через jq, а не склейкой строк - тогда кавычки и переносы экранируются правильно.

Ловушка 3
Запрещать можно только в PreToolUse - потом поздно

Почему так. PostToolUse срабатывает после того, как инструмент отработал: файл записан, команда выполнена. Даже подмена вывода меняет только то, что видит Claude, а не то, что произошло на диске.

Как применить. Всё запретительное - на PreToolUse. На PostToolUse - форматирование, логи, комментарий Claude.

Ловушка 4
Скрипт должен быть исполняемым и вызываться по абсолютному пути

Почему так. Файл не исполняемый или путь относительный - получишь «command not found» и неблокирующую ошибку: действие пройдёт, а защита не сработает.

Как применить. chmod +x .claude/hooks/имя.sh, а в конфиге путь через плейсхолдер "${CLAUDE_PROJECT_DIR}/.claude/hooks/имя.sh" в двойных кавычках.

Ловушка 5
additionalContext всегда кладётся внутрь hookSpecificOutput

Почему так. Положишь на верхний уровень - Claude Code молча проигнорирует, никакой ошибки не увидишь.

Как применить. {"hookSpecificOutput": {"hookEventName": "UserPromptSubmit", "additionalContext": "текст"}}.

⚠️

Хуки одного события выполняются параллельно и все до конца. «Один хук, вернувший запрет, не останавливает выполнение соседних». Побочные эффекты соседа уже произойдут, даже если твой хук запретил действие.

💡

Хуки ужесточают, но не ослабляют. Разрешение из хука не отменяет твои deny-правила. Зато запрет из хука работает даже в bypassPermissions - это самая надёжная защита из существующих.

✅

Хук не видит правок через терминал? Хук на Edit и Write не увидит изменений, сделанных командой оболочки, и аудит окажется дырявым. Бери FileChanged - он следит за файлом на диске независимо от того, кто его переписал (но заблокировать не может), либо Stop-хук, который раз за ход сверяет состояние.

🚫

Безопасность: хук - это выполнение произвольного кода от твоего имени. Дословно: «Хуки выполняют команды оболочки с полными правами твоего пользователя. Они могут изменить, удалить или прочитать любой файл, доступный твоей учётной записи». В режиме -p диалог доверия к папке не показывается, и хуки из чужого репозитория запустятся сами. Перед запуском по чужому репозиторию - просмотри его папку .claude/, либо стартуй с --bare, либо отключи хуки на один запуск.

Промпт: звуковые уведомления
Настрой мне звуковые уведомления через хуки:

1. Звук при завершении работы (событие Stop) - чтобы я слышал, когда ты закончил.
2. Другой звук при запросе разрешения (событие Notification) - чтобы я слышал, когда ты ждёшь моего ответа.

Используй встроенные системные звуки моей операционной системы, два разных - чтобы на слух отличать «готово» от «нужен ты».

Покажи итоговый файл настроек и объясни каждую строку простыми словами. Потом проверь через /hooks, что оба хука подхватились.
⚠️

Проверять надо в новом чате: хуки подхватываются при старте сессии, в текущем окне изменения не применятся. И проверяй через /hooks, а не на глазок: меню показывает, что Claude Code реально прочитал - событие, фильтр, тип, файл-источник и саму команду. Нет там хука - он не сработает никогда.

Промпт: хук-замок на секреты
Поставь мне блокирующий хук на PreToolUse, который физически не даст прочитать файлы с секретами целиком - ни инструментом чтения, ни командами терминала внутри цепочек.

Требования:
- запрет должен возвращать код выхода 2 и писать понятную причину в stderr;
- точечный запрос одной переменной по маске grep '^ИМЯ=' разрешить - это рабочий путь;
- скрипт положи в .claude/hooks/, сделай исполняемым, в конфиге укажи путь через ${CLAUDE_PROJECT_DIR};
- проверь, что jq установлен, если он нужен.

Покажи мне скрипт и объясни его построчно. Потом открой новый чат и проверь вживую: попробуй прочитать файл целиком и покажи, что блокировка сработала.
Продвинутое: хуки с моделью, фоновые хуки, таймауты▼

Хуки с моделью. Иногда правило нельзя записать поиском по тексту - например, «все ли пункты плана закрыты?». Тип prompt отдаёт вопрос быстрой модели (таймаут 30 секунд, ответ строго «да/нет с причиной»). Тип agent поднимает сабагента с доступом к файлам и командам (до 50 ходов, помечен экспериментальным). Для постоянной работы документация советует обычные command-хуки.

Фоновые хуки. "async": true - хук стартует и отпускает Claude дальше. Но помни: его решения уже ни на что не влияют, код выхода не читается. Для логов и уведомлений. Нужно, чтобы фоновый провал всё-таки дошёл - "asyncRewake": true.

Таймауты разные. По умолчанию 600 секунд, но UserPromptSubmit понижает до 30 (иначе тормозит каждый твой запрос), MessageDisplay до 10, а у SessionEnd общий бюджет 1,5 секунды на все хуки вместе - долгий там просто не успеет отработать.

Отладка идёт в файл, а не на экран. Успешный хук не показывает ничего. Запусти claude --debug-file /tmp/claude.log и смотри tail -f /tmp/claude.log в соседнем окне. Ctrl+O открывает подробный вид - там видно, что вернул хук.

Хук не может вызвать команду или инструмент - только вернуть текст и код выхода. Единственный канал влияния на модель - additionalContext, и формулировать его надо фактами («текущая ветка: такая-то»), а не приказами: текст в виде команд может сработать как защита от подсунутых инструкций.

2.5Свои команды: ритуал одной строкой~12 мин▼

Повторяющийся ритуал - разбор ученика, пост в канал, утренний план - оформляется командой /имя и живёт в проекте, накапливая твои правки.

⚠️

Важное изменение 2026 года: свои команды официально слились со скиллами. Страницы про слэш-команды в документации больше нет - старый адрес редиректит на страницу про скиллы. Твои существующие файлы .claude/commands/имя.md продолжают работать, переносить срочно ничего не надо. Но новые команды лучше делать папкой-скиллом: у скилла можно положить рядом вспомогательные файлы и скрипты, и Claude может подхватить его сам, когда он к месту.

Где положитьОхват

Четыре механики внутри команды

Механика 1
Аргументы: $ARGUMENTS - весь текст, $0 - первое слово

Почему так. Самая частая ошибка новичка - думать, что первый аргумент это $1. Нет: отсчёт с нуля. $0 первый, $1 второй.

Как применить. Одна тема одной строкой - $ARGUMENTS. Несколько параметров - $0, $1. Многословное значение оборачивай в кавычки. Можно дать аргументам человеческие имена: arguments: [ученик, тип, дата] в шапке, и дальше писать $ученик.

Механика 2
Восклицательный знак подставляет вывод команды до отправки

Почему так. Claude получает не задание «посмотри состояние», а уже готовые данные. Ответ опирается на реальное положение дел, а не на догадки.

Как применить. Пиши !`команда` с начала строки. Знак срабатывает только в начале строки или сразу после пробела.

Механика 3
Собачка вставляет содержимое файла прямо в запрос

Почему так. Файл попадает в промпт без вызова инструмента - быстрее, чем просить прочитать.

Как применить. @путь/к/файлу.md прямо в тексте команды.

Механика 4
Действия с последствиями закрывай от автозапуска

Почему так. Иначе Claude может решить, что всё готово, и сам вызвать команду публикации. Дословно: «ты же не хочешь, чтобы Claude решал развернуть проект, потому что код выглядит готовым».

Как применить. В шапку: disable-model-invocation: true - тогда команду запускаешь только ты.

🚫

Шапка файла читается, только если три дефиса стоят первой строкой. Есть перед ними хоть пустая строка - и весь файл, вместе с дефисами, считается обычным текстом. Команда запустится, но описания у неё не будет, и Claude не поймёт, когда её применять.

⚠️

Содержимое вызванной команды остаётся в контексте до конца разговора - это не одноразовая вставка. Каждая строка - постоянный расход. Держи файл коротким (документация советует до 500 строк), длинные справочники выноси в соседние файлы. И пиши что делать, а не почему.

💡

Разрешения из allowed-tools действуют ровно один ход - тот, в котором ты вызвал команду, и снимаются со следующим твоим сообщением. Нужно на всю сессию - добавляй правила в настройки.

✅

Правки подхватываются на лету, перезапуск не нужен. Но новая папка скилла, которой не было при старте, требует перезапуска. Ручное обновление - /reload-skills. Управлять списком удобно через /skills: показывает всё доступное, сортирует по цене в токенах и умеет прятать лишнее.

Промпт: сделать свою команду из ритуала
Сделай мне свою команду из ритуала, который я повторяю руками.

Ритуал: [ОПИШИ СВОИМИ СЛОВАМИ, что ты делаешь каждый раз и в каком порядке].

Требования:
- сделай папкой-скиллом (.claude/skills/имя/SKILL.md), а не файлом в commands - так рекомендует свежая документация;
- три дефиса шапки строго первой строкой файла;
- description напиши теми словами, которыми я реально формулирую эту задачу вслух;
- если у команды есть параметры - дай им человеческие имена через arguments, а не $0 и $1;
- если ритуал заканчивается действием с последствиями (отправка, публикация) - поставь disable-model-invocation: true;
- держи файл коротким, длинные справочники вынеси в соседние файлы рядом.

Покажи готовый файл, объясни каждую строку и скажи, как его вызывать.
2.6Стиль ответа и статусная строка~8 мин▼
Правило
Стиль ответа меняет как Claude говорит. CLAUDE.md - что он знает про твой проект

Почему так. Это два разных механизма. Стиль переписывает системный промпт: роль, тон, формат. CLAUDE.md приезжает отдельным сообщением после него и несёт факты о проекте. Запихнёшь правила проекта в стиль - они начнут конфликтовать с настройками Claude Code. Запихнёшь тон в CLAUDE.md - он будет слабее действовать на формат каждого ответа.

Как применить. Проверь себя вопросом: «это про манеру речи и формат ответа?» - стиль. «Это про мои файлы, папки и договорённости?» - CLAUDE.md.

🚫

Команда /output-style удалена. Прочитаешь старую инструкцию в интернете - команда просто не найдётся. Стиль выбирается через /config, пункт Output style.

⚠️

Смена стиля вступает в силу только после /clear или новой сессии. Стиль - часть системного промпта, а он читается один раз при старте. Поменяешь посреди разговора - ничего не изменится, и решишь, что не работает.

💡

Свой стиль вырезает встроенные инженерные инструкции Claude Code - как ограничивать объём правок, как проверять результат. Для помощника по текстам это правильно. Если работаешь с кодом и хочешь поменять только подачу - поставь в шапке keep-coding-instructions: true.

💡

Стиль действует только на главный разговор, не на сабагентов - у них свой системный промпт. Нужен отдельный тон под конкретную задачу - это не стиль, а сабагент (часть 4).

Статусная строка

Claude Code не рисует её сам: он запускает твой скрипт, отдаёт ему данные сессии (модель, папка, токены, лимиты) и показывает то, что скрипт напечатал. Отсюда все ошибки: скрипт молчит - строка пустая, скрипт медленный - строка тормозит.

✅

Скрипт писать руками не надо. Набери /statusline и опиши словами, что хочешь видеть. Claude Code создаст файл и сам пропишет его в настройки.

✅

Статусная строка ничего не стоит: «работает локально и не потребляет токены API». Выводи туда всё, что нужно - на счёт это не влияет.

Промпт: полезная статусная строка
/statusline покажи название модели, процент заполнения контекста с полоской прогресса, текущую папку и остаток лимитов до сброса
Часть 3

Скиллы: навыки, которые Claude берёт сам

Курс «Introduction to agent skills» целиком. Его смысловое ядро - одна фраза с обложки: перестань повторяться и научи Claude один раз. Скилл - это многоразовая инструкция в обычном текстовом файле, которую Claude подхватывает сам, когда задача ей соответствует.

3.1Что такое скилл и когда он нужен~10 мин▼
Правило
Заводи скилл, когда одну и ту же инструкцию вставляешь в чат второй-третий раз

Почему так. Пока инструкция живёт в голове или в переписке, ты каждый раз копируешь её по-разному. Скилл фиксирует процедуру один раз, и она применяется одинаково во всех сессиях. Дословный триггер из документации: «создавай скилл, когда постоянно вставляешь одни и те же инструкции, чек-лист или многошаговую процедуру в чат, или когда раздел CLAUDE.md разросся в процедуру, а не остался фактом».

Как применить. Папка плюс файл: ~/.claude/skills/имя-скилла/SKILL.md. Имя папки становится командой: папка razbor-uchenika даёт /razbor-uchenika.

Главное разграничение курса
Процедуры - в скилл. Факты - в CLAUDE.md

Почему так. CLAUDE.md грузится всегда и стоит токенов в каждой сессии. Тело скилла грузится только когда он сработал, поэтому длинный справочный материал в скилле «почти ничего не стоит, пока он тебе не нужен».

Как применить. Пройди по своему CLAUDE.md: раздел отвечает на вопрос «что где лежит» - это факт, оставь. Отвечает на вопрос «как это делать по шагам» - переноси в скилл.

Четыре механизма настройки - чем отличаются

Отдельный урок курса называется «Skills vs. other Claude Code features». Короткая карта:

МеханизмКогда действуетДля чего
CLAUDE.mdВсегда, каждая сессияФакты и постоянные правила проекта
СкиллКогда вызван или подошёл под задачуПроцедуры, чек-листы, многошаговые ритуалы
ХукВсегда, на событие, программноГарантии: запреты, проверки, уведомления
СабагентКогда делегировали задачуОтдельный контекст и своя роль под задачу

Минимальный скилл

Файл ~/.claude/skills/имя/SKILL.md
---
name: имя-скилла
description: Что делает скилл и когда его применять
---

# Название

## Инструкции
Пошаговые указания для Claude.

## Примеры
Конкретные примеры применения.

Обязательных полей два: name и description. Требования к имени: до 64 символов, только строчные латинские буквы, цифры и дефисы, без слов anthropic и claude - они запрещены.

✅

Прогрессивная загрузка - тот самый принцип, ради которого всё устроено именно так. Claude всегда видит только описание скилла (пара строк). Тело файла подгружается, только когда скилл понадобился. А тяжёлые справочники, лежащие рядом в папке, - только когда Claude решит их открыть. Так можно держать сто скиллов, не платя за них контекстом.

3.2Description: главное поле, от которого всё зависит~10 мин▼

Отдельный урок курса посвящён тому, как «составить работающие описания, по которым навык надёжно срабатывает». Причина проста: description - единственное, что Claude видит всегда, ещё до открытия скилла. По нему он и решает, подходит ли скилл под твой запрос.

Правило
Пиши в description две вещи: что скилл делает и когда его применять

Почему так. Без части «когда» скилл будет либо молчать, либо лезть не в те задачи.

Как применить. Формула: сначала действия, потом «Use when...» с триггерами. Пример из документации: «Extract text and tables from PDF files, fill forms, merge documents. Use when working with PDF files or when the user mentions PDFs, forms, or document extraction».

Правило
Описание - в третьем лице, не от «я» и не от «ты»

Почему так. Описание вставляется в системный промпт. Разнобой в лице мешает модели правильно выбирать скилл. Документация помечает это предупреждением.

Как применить. Хорошо: «Обрабатывает таблицы и собирает отчёт». Плохо: «Я помогу тебе обработать таблицы», «Ты можешь использовать это, чтобы...».

Правило
Ключевой сценарий - первым предложением

Почему так. Описание в общем списке скиллов обрезается на 1536 символах. Если скиллов много, хвост описания может отрезаться вместе с ключевыми словами, по которым скилл должен был сработать.

Как применить. Первое предложение - главное действие и главный триггер. Нюансы дальше. Лимит самого поля - 1024 символа.

✅

Самый практичный совет курса: пиши description теми словами, которыми ты реально формулируешь задачу вслух. Не «генерация аналитического отчёта по данным», а «разбери выгрузку и скажи, что в ней важного» - если ты просишь именно так.

🚫

Скилл не срабатывает? В 9 случаях из 10 дело в description, а не в теле. Порядок починки: 1) добавь в описание слова, которые произносишь вслух; 2) спроси у Claude «какие скиллы доступны?» и проверь, что он в списке; 3) переформулируй запрос ближе к описанию; 4) вызови вручную /имя. Если сломан YAML, скилл вызовется вручную, но описания у него не будет - смотри ошибку разбора через --debug.

3.3Как писать скиллы, которые работают~15 мин▼
Правило
Тело SKILL.md - короче 500 строк, всё длинное в соседние файлы

Почему так. Загруженный скилл остаётся в контексте до конца разговора. Каждая строка - повторяющаяся плата токенами на каждом следующем ходе.

Как применить. В SKILL.md - обзор и навигация. Детали рядом: reference.md, examples.md, и ссылка на них из SKILL.md. Ссылки делай на один уровень вглубь: если файл ссылается на файл, который ссылается на третий, Claude может прочитать их частично и получить неполную картину.

Правило
Скилл должен добавлять только то, чего Claude не знает

Почему так. Документация называет контекстное окно общественным благом: твой скилл делит его с системным промптом, историей разговора и описаниями всех остальных скиллов. Объяснение общеизвестного - чистая потеря места.

Как применить. К каждому абзацу три вопроса из документации: «Нужно ли Claude это объяснение? Могу ли я считать, что он это знает? Оправдывает ли абзац свою цену в токенах?»

Правило
Степень свободы подбирай под хрупкость задачи

Почему так. Аналогия из документации: узкий мост над обрывом против открытого поля. Там, где вариантов много и решает контекст, жёсткая инструкция мешает. Там, где шаг легко сломать, свободная формулировка приводит к ошибке.

Как применить. Высокая свобода - текстовые шаги: «проанализируй структуру, найди слабые места, предложи улучшения». Низкая свобода - точная команда с оговоркой «не меняй команду и не добавляй флаги».

Четыре антипаттерна

  • Разнобой в терминах. «Поле», «блок», «элемент» про одно и то же - выбери один термин на понятие и держись его во всех файлах скилла.
  • Даты и привязки ко времени. «До августа используй старое, после - новое» через год станет вредной инструкцией. Актуальный способ - в основном разделе, устаревшее - в свёрнутом блоке «старые подходы».
  • Куча альтернатив. Перечисление пяти инструментов запутывает. Дай один вариант по умолчанию и одну строчку про исключение.
  • Разовые формулировки. «Сначала сделай X» после первого ответа перестаёт работать как напоминание - скилл не перечитывается. Пиши постоянные правила: «всегда фильтруй тестовые записи».
✅

Имя скилла - в форме действия. Рекомендуемая форма - герундий: processing-pdfs, analyzing-spreadsheets. Плохо: helper, utils, tools, data, files - они не говорят ни о чём. Имена файлов внутри тоже говорящие: Claude ходит по папке как по файловой системе и решает по имени, стоит ли открывать.

Как проверять скилл

Правило
Проверяй скилл в свежей сессии, а не в той, где писал

Почему так. В сессии, где ты объяснял задачу словами, остаточный контекст маскирует дыры в написанной инструкции: кажется, что скилл работает, а работает твой прошлый разговор.

Как применить. Собери несколько реальных запросов, прогони каждый в новой сессии, потом повтори с выключенным скиллом и сравни результаты.

💡

Разработка от проверок. Документация называет это evaluation-driven development: сначала прогони задачу без скилла и запиши конкретные провалы, потом собери три сценария на эти провалы, замерь базовый результат, напиши минимальный текст, закрывающий именно их, и замерь снова. Так решаешь настоящие проблемы, а не выдуманные.

✅

Приём «два Claude». Один пишет и сокращает скилл, второй в свежем окне показывает реальные дыры. Возвращаешься к первому с конкретным наблюдением: «забыл отфильтровать тестовые записи» - и он правит.

Промпт: собрать скилл из повторяющейся процедуры
Собери скилл из процедуры, которую я повторяю каждый раз руками.

Процедура: [ОПИШИ СВОИМИ СЛОВАМИ, что и в каком порядке ты делаешь].

Требования по документации Anthropic:
- description в третьем лице, формула «что делает + Use when + триггеры», ключевой сценарий первым предложением;
- слова в описании возьми те, которыми я реально формулирую эту задачу вслух - спроси меня, как я обычно её называю;
- тело SKILL.md короче 500 строк, всё длинное вынеси в соседние файлы и сошлись на них из SKILL.md на один уровень;
- один термин на понятие, никаких дат, один вариант по умолчанию вместо списка альтернатив;
- имя папки в форме действия, без helper и utils;
- если процедура заканчивается действием с последствиями - disable-model-invocation: true.

Сначала задай мне уточняющие вопросы про шаги, которые я мог упустить. Потом покажи готовый файл и объясни, как проверить, что скилл срабатывает.
Промпт: скилл не срабатывает - починить
Мой скилл [ИМЯ] не срабатывает сам, когда я прошу [ФОРМУЛИРОВКА, КОТОРУЮ Я ИСПОЛЬЗУЮ].

Проверь по порядку:
1. Виден ли скилл вообще - перечисли, какие скиллы тебе сейчас доступны.
2. Не сломана ли шапка файла: три дефиса должны быть первой строкой.
3. Есть ли в description слова из моей формулировки. Если нет - перепиши description так, чтобы он срабатывал именно на неё, сохранив формулу «что делает + когда применять».
4. Не обрезается ли описание: проверь длину.

Покажи, что именно поменял, и проверь в новой сессии.

🚫

Ставь скиллы только из доверенных источников. Скилл даёт Claude новые инструкции и код - вредоносный может заставить его вызывать инструменты не по назначению. Документация советует относиться к установке скилла как к установке программы: прочитай все файлы - SKILL.md, скрипты, ресурсы. Ищи неожиданные обращения в сеть и операции, не связанные с заявленной целью.

🚫

Отдельно проверяй поле allowed-tools в чужих проектных скиллах. Доверие к папке от этого не защищает: Claude Code применяет allowed-tools проектного скилла даже в папке, которой ты никогда не доверял, в том числе при запуске с флагом -p. Скилл может выдать себе широкий доступ. Перед первым запуском в чужом репозитории открой .claude/skills/*/SKILL.md и посмотри эти строки.

⚠️

Личный скилл из ~/.claude/skills/ не работает в облачных сессиях. Облако не читает твою машину. Для облачных запусков скилл надо либо закоммитить в репозиторий, либо упаковать в плагин.

Часть 4

Сабагенты: делегирование и чистый контекст

Курс «Introduction to subagents» целиком. Главная мысль, которую он вбивает: сабагент - это способ управлять памятью, а не просто «ещё один помощник».

4.1Зачем сабагент и когда он оправдан~10 мин▼

Сабагент уходит «в свою комнату» с чистой памятью, делает работу и возвращает только выжимку, а не гору черновиков. Дословно из курса: они «позволяют делегировать задачи изолированным помощникам, которые делают работу отдельно и возвращают ровно ту информацию, которая тебе нужна, сохраняя главное окно контекста чистым».

Правило
Делегируй, когда работа объёмная, а результат должен быть коротким

Почему так. Дословный признак из документации: «используй сабагента, когда побочная задача завалила бы основной разговор результатами поиска, логами или содержимым файлов, к которым ты больше не вернёшься».

Как применить. Перед тяжёлой задачей спроси себя: сколько сырья придётся перелопатить, чтобы получить один короткий вывод? Много - отдавай сабагенту.

Правило
Сабагент не видит твою переписку - вписывай контекст в задание явно

Почему так. Он работает в отдельном окне контекста. Люди удивляются, почему он «не знает», о чём ты говорил полчаса назад - а он и не мог знать.

Как применить. В задание пиши всё: какие файлы читать, что искать, в каком виде вернуть ответ.

🚫

Когда сабагент не нужен (отдельный урок курса про анти-паттерны): задача короткая; нужны твои живые уточнения по ходу; тебе важен весь материал целиком, а не выжимка. Делегировать простое - лишний круг: теряешь время на объяснение и получаешь пересказ вместо прямого ответа.

⚠️

Не плоди сабагентов ради красоты. Прямое предупреждение: «когда сабагенты завершаются, их результаты возвращаются в основной разговор. Много сабагентов, каждый из которых возвращает подробный отчёт, съедят значительный контекст». Двадцать подробных отчётов забьют чат так же, как если бы ты делал всё сам. Лимит одновременных - 20.

💡

Сабагент и форк - разные вещи. Сабагент стартует с чистой памятью и своей инструкцией. Форк (/subtask) наследует весь текущий разговор: ту же историю, тот же промпт, ту же модель. Задача опирается на предыдущий разговор («напиши по тому, что мы сейчас обсудили») - форк. Задача самодостаточна - сабагент.

4.2Как создать своего~12 мин▼

Сабагент - это markdown-файл: шапка с настройками между строками из трёх дефисов, ниже - инструкция обычным текстом. Больше ничего не нужно.

Файл .claude/agents/имя.md
---
name: post-checker
description: Проверяет черновик поста на соответствие тону и стоп-словам. Использовать после написания любого текста.
tools: Read, Grep, Glob
model: sonnet
---

Ты проверяющий редактор. Прочитай черновик и правила тона.

Верни ровно три блока:
- Нарушения тона: максимум 7 пунктов, каждый с цитатой
- Стоп-слова: список найденных с номерами строк
- Что усилить: максимум 3 пункта

Если файла с правилами нет или данных не хватает - не додумывай,
напиши отдельной строкой, что именно помешало.
Где лежитОхват
~/.claude/agents/имя.mdЛичный, во всех твоих проектах
.claude/agents/имя.mdПроектный, уезжает в репозиторий команде

При совпадении имён проектный побеждает личного. Имя - только строчные латинские буквы и дефисы, без двоеточия.

Правило
description - это не описание для человека, а триггер делегирования

Почему так. Claude решает, звать сабагента или нет, по трём вещам: твоей формулировке, полю description и текущему контексту. Расплывчатое описание - сабагент не вызывается. Дословно: «"Анализирует код" слишком размыто; "Проверяет код на проблемы производительности и предлагает оптимизации" говорит Claude точно, когда его применять».

Как применить. Пиши когда именно применять, а не что это такое. Чтобы Claude звал агента сам, без напоминаний, добавь в описание «использовать проактивно».

Правило
Один сабагент - одна чётко очерченная задача

Почему так. Дословно: «Сабагент, который пытается делать всё, теряет само преимущество изоляции контекста». Универсальный агент-всё-умею превращается во второй основной чат, только хуже.

Как применить. Вместо одного «помощник по контенту» - три: проверяющий текст, собирающий выжимку из расшифровки, сверяющий цифры. Каждому своё описание и свой набор инструментов.

Правило
Ограничивай инструменты - это и безопасность, и скорость

Почему так. Без ограничений сабагент наследует все инструменты основного разговора, включая запись и удаление файлов. Проверяющему право писать в файлы просто не нужно. Дословно: «удаление ненужных инструментов держит сабагентов сфокусированными и делает их быстрее».

Как применить. Белый список: tools: Read, Grep, Glob - доступны только эти три. Чёрный список: disallowedTools: Write, Edit - унаследуется всё, кроме записи и правки.

Правило
Подбирай модель под сложность - это способ управлять расходом

Почему так. Дословно: «контролируй расходы, направляя задачи на более быстрые и дешёвые модели вроде Haiku». Быстрая модель отлично справляется с узкой механикой.

Как применить. model: haiku - собрать список, проверить по чек-листу. model: sonnet - обычная работа. model: opus - сложный анализ, аудит. По умолчанию inherit - та же модель, что в основном чате.

🚫

Claude Code молча пропускает файл с битой шапкой и не сообщает об этом в сессии. Ты будешь думать, что агент есть, а его нет. Причины: нет name; открывающие дефисы не на первой строке; имя начинается с дефиса или содержит двоеточие; есть имя, но нет описания; YAML не разбирается. Проверить: claude --debug и посмотреть лог, или claude plugin validate .claude/agents.

💡

Файлы подхватываются на лету, но перезапуск нужен, если ты создал первый файл агента в новой папке, которой не было при старте сессии.

4.3Три приёма надёжности из курса~10 мин▼

Отдельный урок курса называется «Designing effective subagents» и даёт ровно три паттерна: структурированный формат вывода, сообщение о препятствиях и ограничение инструментов.

Приём 1
Надёжность даёт структура ответа, а не длинное задание

Почему так. Без заданного формата сабагент вернёт кашу, которую придётся разбирать руками. И тем самым съест ровно тот контекст, ради экономии которого его и звали.

Как применить. Задай шаблон прямо в инструкции: «верни ровно 3 блока - Находки / Риски / Что делать дальше, в каждом максимум 5 пунктов».

Приём 2
Сабагент обязан сообщать о препятствии, а не молча выдавать половину

Почему так. В курсе это отдельный элемент проектирования - obstacle reporting. Молчаливо неполный результат опаснее честного «не смог»: ты примешь решение на дырявых данных и не узнаешь об этом.

Как применить. Добавь в инструкцию фразу: «Если файла нет, доступа нет или данных не хватает - не додумывай. Напиши, что именно помешало, и верни то, что реально удалось собрать».

Приём 3
Меньше прав - меньше шансов на необратимую ошибку

Почему так. Сабагенту-аналитику не нужны права менять, удалять и отправлять наружу. Это ровно тот случай, когда ограничение ничего не стоит.

Как применить. Читателю-аналитику оставь чтение и поиск, без записи файлов и без выхода в интернет.

🚫

Особая осторожность с permissionMode: bypassPermissions у сабагента. Он пропускает все запросы и позволяет писать в служебные папки, включая .git и .claude - то есть агент может незаметно переписать твою же конфигурацию. Включай только осознанно и только агенту с урезанным списком инструментов.

Как вызывать

  • Словами: «используй сабагента такого-то, чтобы...». Автоделегирование вероятностное - Claude может решить сделать сам.
  • Через @: набрать @ и выбрать из подсказки.
  • Всю сессию от лица агента: claude --agent имя.
✅

Цепочки и параллель - одной фразой. Параллель: «изучи эти три темы параллельно, каждую отдельным сабагентом». Цепочка: «сначала сабагент-проверяющий найдёт проблемы, потом сабагент-исполнитель их исправит» - так «найти» и «починить» разводятся на два независимых прохода, и второй не защищает работу первого.

💡

Незаконченного сабагента можно продолжить, а не запускать заново: он сохраняет полную историю своего разговора. Просто скажи в чате: «продолжи ту проверку и разбери теперь вот это».

💡

Для повторяющейся работы дай сабагенту память: поле memory: project даёт ему постоянную папку, которая переживает завершение разговора - так копятся наблюдения и повторяющиеся ошибки. Документация называет это обучением между сессиями. И проси его: «проверь свою память перед работой», «сохрани, что узнал».

Промпт: создать сабагента под свою повторяющуюся задачу
Создай мне сабагента в .claude/agents/ под задачу, которую я повторяю постоянно.

Задача: [ОПИШИ - например: проверять черновик текста по моим правилам тона и возвращать только замечания].

Собери его по правилам курса Anthropic про сабагентов:
- description напиши как ТРИГГЕР («использовать после того-то»), а не как описание для человека;
- задай жёсткий формат ответа: ровно N блоков, в каждом максимум M пунктов, без пересказа исходника;
- добавь обязательное сообщение о препятствиях: если данных не хватило - сказать, что именно помешало, и не додумывать;
- ограничь инструменты только теми, без которых он не справится - права на запись не давай;
- подбери модель под сложность задачи и объясни выбор.

Покажи готовый файл, объясни каждое поле и проверь его на реальном примере в новой сессии.
Промпт: разведка сабагентом без засорения контекста
Отправь сабагента разобраться, как в этом проекте устроено [ТЕМА], и что из существующего можно переиспользовать вместо того, чтобы делать заново.

Пусть он прочитает всё нужное в своём окне контекста, а мне вернёт только:
- выводы, максимум 10 пунктов;
- список ключевых файлов с одной строкой пояснения на каждый;
- отдельной строкой - что помешало, если чего-то не хватило.

Без пересказа содержимого файлов. В конце скажи, сколько примерно он прочитал и сколько вернулось в мой контекст.
4.4Сверх сабагентов: несколько Claude одновременно~12 мин▼

Этого нет ни в одном курсе, но это следующая ступень после сабагентов. Способов «делать много дел сразу» четыре, и они решают разные задачи.

Правило
Выбирай подход по вопросу «кто держит план»

Почему так. Возьмёшь команду агентов там, где хватило бы одного сабагента - заплатишь в несколько раз больше и получишь хаос из-за координации. Возьмёшь сабагента там, где нужен сценарий - он не удержит в голове сотни файлов.

Как применить. Три вопроса из документации: кто координирует? Нужно ли работникам говорить друг с другом? Трогают ли задачи одни и те же файлы?

СпособКто держит планКогда брать
СабагентыClaude внутри одного разговораПобочная работа, нужен только вывод
Панель агентовТы раздаёшь и проверяешь позжеНесколько независимых задач «раздал и забыл»
Команды агентовClaude планирует и надзирает за группойИсследование и ревью большим фронтом
Сценарии (workflows)План лежит в скрипте, а не в головеСотни однотипных единиц работы

Панель агентов: раздал и забыл

Команда claude agents открывает единственный экран, где видно все фоновые сессии сразу: что работает, что закончено, а что ждёт твоего ответа. Без него будешь переключаться между терминалами и не заметишь, что одна сессия час стоит на вопросе о разрешении.

  • Space - подглядеть последний вывод, не заходя внутрь.
  • Enter - зайти в разговор целиком.
  • Жёлтая строка - нужен твой ответ, зелёная - готово.
🚫

Главная неожиданность: фоновые сессии по умолчанию уезжают в отдельную копию проекта перед первой правкой файла - чтобы три сессии не переписали один файл. Новичок открывает свою папку, не видит изменений и думает, что Claude ничего не сделал. Claude в конце обязан отчитаться, где лежит результат.

💡

Если тебе эта изоляция мешает (у тебя не код, а папка с текстами) - её выключают настройкой в проекте, и тогда фоновые сессии правят рабочую копию напрямую.

⚠️

Вне git-репозитория изоляции нет вообще. Дословно: «за пределами git-репозитория сессии пишут в рабочую папку напрямую и не изолированы друг от друга». Две сессии спокойно затрут правки друг друга. В обычной папке с документами - либо запускай по одной, либо разводи их по разным файлам прямо в тексте задачи.

Четыре команды, которые путают

/backgroundУбрать этот разговор в фон, освободить терминал. Псевдоним /bg
/forkСделать копию разговора в новую фоновую сессию, обе живут независимо
/branchВетка разговора, и ты сам переходишь в неё; оригинал сохраняется
/subtaskОтдать побочную задачу, результат вернётся сюда же
🚫

Команды агентов - экспериментальная функция, и у неё коварная ловушка. Когда они включены, любой сабагент, которому Claude сам дал имя, запускается как полноценный участник команды. То есть команда может собраться сама, хотя ты её не просил, и токены полетят кратно быстрее.

Часть 5

Длинные сессии без присмотра

Разделы Steer the Work и Verify and Share из курса in Action плюс официальные лучшие практики Anthropic. Это про то, как дать Claude работу на несколько часов, уйти и потом уверенно проверить, что он сделал.

5.1Одно ограничение, из которого следует всё остальное~7 мин▼
🎯

Дословно из статьи Anthropic: «Большинство лучших практик основаны на одном ограничении: окно контекста Claude заполняется быстро, и качество падает по мере заполнения». Контекст назван «самым важным ресурсом, которым нужно управлять».

Из этого выводятся почти все приёмы курса. Пять следствий:

1

/clear между несвязанными задачами.

2

Исследование - сабагентам, чтобы чтение сотни файлов не попало в твой контекст.

3

CLAUDE.md коротким.

4

Заполнение видно в строке состояния - настроить её один раз.

5

Управляемое сжатие с фокусом вместо ожидания, пока автосжатие сработает само.

5.2Проверка: четыре уровня жёсткости~15 мин▼
Центральное правило курса
Дай Claude проверку, которую он может запустить сам

Почему так. Claude останавливается, когда работа выглядит законченной. Без проверки «выглядит» - единственный доступный ему сигнал, и проверяющим циклом становишься ты: каждая ошибка ждёт, пока ты её заметишь. Если есть что-то, возвращающее «прошло / не прошло», цикл замыкается сам. Дословно: это разница между сессией, которую ты смотришь, и сессией, от которой можно отойти.

Как применить. Проверкой может быть что угодно с читаемым сигналом: набор тестов, результат сборки, скрипт сверки с эталоном, скриншот в сравнении с макетом. Для не-кодовых задач - перечитать файл и сверить с исходником, пересчитать цифры, проверить наличие обязательных блоков.

Четыре уровня, от мягкого к железному

УровеньКак выглядитКогда
1. В промпте«сделай, запусти проверку и правь, пока не пройдёт»Обычная задача
2. На всю сессиюУсловие через /goal: отдельный оценщик перечитывает его после каждого ходаДлинная работа с чёткой целью
3. ШлагбаумStop-хук: не даёт закончить ход, пока проверка не прошлаТребование, которое нельзя пропустить
4. Второе мнениеСабагент-проверяющий или второй Claude в свежем окнеВажный результат, нужен независимый взгляд
⚠️

У шлагбаума есть предел: Claude Code перебивает Stop-хук и завершает ход после 8 блокировок подряд - иначе сессия зациклилась бы навсегда.

Правило
Требуй доказательство, а не заявление «готово»

Почему так. Дословно: «Пусть Claude показывает доказательство, а не утверждает успех: вывод теста, саму команду и что она вернула, или скриншот результата». Читать доказательство быстрее, чем перепроверять руками.

Как применить. Добавляй в конец каждого задания: «покажи, что именно ты запустил и что оно вернуло».

Правило курса in Action
Проверяй результат пропорционально тому, насколько мало ты смотрел за работой

Почему так. Дословная формулировка курса: «verify unsupervised runs in proportion to how little you watched them». Чем дольше Claude работал один, тем выше шанс тихой ошибки, которую не видно в финальном отчёте.

Как применить. После длинного автономного прогона выдели отдельный шаг: попроси показать список всех изменённых файлов и обоснование каждого решения, и сверь выборочно 2-3 самых важных сам.

Промпт: приёмка автономного прогона
Ты работал без моего присмотра. Теперь отчитайся так, чтобы я мог проверить тебя за 5 минут:

1. Полный список файлов, которые ты создал или изменил, с одной строкой: что именно в каждом изменилось.
2. По каждому нетривиальному решению - почему выбрал этот вариант и какие были альтернативы.
3. Что ты проверял и чем: покажи команды и их вывод, а не слова «работает».
4. Что осталось непроверенным и где ты не уверен. Здесь отвечай честно, без сглаживания - это самый важный пункт.
5. Что ты сделал сверх задачи, если такое было.

Ничего не исправляй, пока я не скажу. Сейчас мне нужна только картина.
Промпт: задача с самопроверкой в цикле
Задача: [ЧТО НУЖНО СДЕЛАТЬ].

Критерий готовности: [ЧЕМ ПРОВЕРЯТЬ - конкретно и проверяемо].

Работай в цикле: сделал - проверил - если не прошло, исправил и проверил снова. Не останавливайся, пока проверка не пройдёт.

В конце покажи доказательство: что именно ты запустил и что оно вернуло. Слово «готово» без доказательства не принимается.

Если ты трижды не смог пройти проверку - остановись и напиши, что мешает, вместо новых попыток.
5.3Как формулировать, чтобы получалось с первого раза~12 мин▼

В статье Anthropic есть таблица «плохо / хорошо» с четырьмя приёмами. Это самое практичное, что вообще есть по промптам для Claude Code.

ПриёмПлохоХорошо
Сузить задачу «напиши тесты для файла» «напиши тест на случай, когда пользователь вышел из системы; без заглушек»
Указать источник ответа «почему тут такой странный интерфейс?» «посмотри историю изменений этого файла и объясни, как интерфейс стал таким»
Сослаться на образец «сделай новый блок» «посмотри, как сделаны существующие блоки на главной; вот хороший пример; следуй этому шаблону»

💡

Расплывчатый промпт - тоже инструмент, но осознанный. Вопрос «что бы ты здесь улучшил?» вытаскивает то, о чём ты не догадался спросить. Правило: расплывчатость на разведке, конкретика на исполнении. Не наоборот.

Правило
Подавай богатый материал, а не описание материала

Почему так. Прочитанный файл, картинка или страница документации точнее любого пересказа.

Как применить. Пять способов: @ перед путём; вставить картинку напрямую копипастом или перетаскиванием; дать ссылку на документацию; подать данные через конвейер; попросить Claude добыть контекст самому.

Правило
Для крупной задачи пусть Claude сначала проинтервьюирует тебя

Почему так. Он спросит про то, о чём ты ещё не подумал: реализацию, интерфейс, краевые случаи, компромиссы. Дословно: «Время, потраченное на уточнение спецификации, окупается лучше, чем время, потраченное на наблюдение за исполнением».

Как применить. Интервью → запись в SPEC.md → свежая сессия для исполнения: чистый контекст целиком под работу плюс письменная спецификация под рукой. Хорошая спецификация самодостаточна: называет файлы, говорит, что вне рамок, и заканчивается сквозной проверкой.

✅

Задавай Claude вопросы, которые задал бы старшему коллеге. «Как здесь устроено то-то?», «Почему сделано так, а не иначе?», «Какие краевые случаи учтены?». Никакого особого промптинга не нужно - это самый быстрый способ войти в незнакомый материал.

Внешние сервисы: командные утилиты экономнее всего

💡

Дословно: «Утилиты командной строки - самый экономный по контексту способ работать с внешними сервисами». Незнакомую утилиту Claude осваивает сам: «изучи справку этой утилиты и реши с её помощью такие-то задачи».

5.4Принципы Anthropic: как вообще строить работу с агентом~8 мин▼

Это не из курсов, а из инженерных статей Anthropic. Четыре принципа, которые стоят за всем остальным.

Принцип 1
Начинай с самого простого, сложность добавляй только когда простое доказано не тянет

Почему так. Дословно: «самые успешные реализации используют простые составные приёмы, а не сложные конструкции». Сложное дороже, медленнее и труднее чинить, потому что прячет от тебя настоящие промпты и ответы.

Как применить. Прежде чем городить скилл, сабагента и хуки - попробуй решить задачу одним хорошим промптом. Не вышло - добавь один слой. Всё ещё нет - добавь второй.

Принцип 2
Не пиши скилл из головы - сначала посмотри, где Claude реально спотыкается

Почему так. Дословно: «выяви конкретные пробелы, прогнав агента на типовых задачах и наблюдая, где он буксует или требует дополнительного контекста. Потом наращивай скиллы, закрывая именно эти недостатки». Скилл, написанный наугад, лечит несуществующие болезни и ест контекст.

Как применить. Возьми 3-5 типовых задач, прогони без скилла и запиши, где пришлось поправлять. Именно эти поправки и становятся телом скилла.

Принцип 3
Пиши скиллы и правила вместе с Claude, а не в одиночку

Почему так. Дословно: «попроси Claude зафиксировать удачные подходы и типичные ошибки в переиспользуемый скилл. Если он сбился, попроси разобрать, что пошло не так. Так ты выяснишь, какой контекст ему на самом деле нужен, вместо того чтобы угадывать заранее».

Как применить. После удачной задачи: «заверни то, что мы сейчас сделали, в скилл - удачные ходы и ошибки, которых надо избегать». После неудачной: «разбери, почему вышло не то, и допиши скилл, чтобы это не повторилось».

Принцип 4
Контекст - это общественное благо, а не твой личный карман

Почему так. Твой скилл делит окно с системным промптом, историей разговора и описаниями всех остальных скиллов. Каждая лишняя строка отбирает место у чего-то нужного.

Как применить. Три вопроса к каждому абзацу любой инструкции: «Нужно ли Claude это объяснение? Могу ли я считать, что он это знает? Оправдывает ли абзац свою цену в токенах?»

✅

Отсюда же и главное разграничение всей системы, дословно из документации: «CLAUDE.md грузится каждую сессию, поэтому включай туда только то, что применимо широко. Доменные знания и рабочие процессы, нужные лишь иногда, - в скиллы». Проще: факты в CLAUDE.md, процедуры в скиллы.

Часть 6

Автоматизация: расписание, безголовый режим, плагины

Раздел Automate Repeat Work из курса in Action плюс то, чего в курсах нет: полная механика расписаний, автономных циклов и упаковки своей настройки в плагин.

6.1Работа по расписанию: три площадки~12 мин▼

Первое решение - где задача должна выполняться. Ошибёшься здесь, и она просто не сработает.

ПлощадкаРаботаетКогда выбирать
Routines (облако)Даже когда компьютер выключенНужна надёжность без твоей машины
Задачи в десктопеНа твоей машинеНужен доступ к локальным файлам
/loopТолько внутри текущего разговораПодежурить в открытой сессии

🚫

Задачи /loop живут только внутри текущей сессии. Новый разговор стирает все запланированные задачи, закрыл терминал - они больше не сработают. Должно пережить закрытие окна - это Routines или десктопные задачи.

Правило
Промпт для задачи по расписанию пиши так, будто спросить уже будет не у кого

Почему так. Дословно: «Задача выполняется автономно, поэтому не может задать уточняющих вопросов». Всё, что не описано, будет достроено догадкой.

Как применить. Формула: что проверить → что сделать с находками → куда положить результат. И обязательно: «если данных для вывода не хватило, так и напиши, не додумывай».

Механика /loop

  • С интервалом: /loop 5m проверь то-то или /loop проверь то-то каждые 2 часа. Единицы: s, m, h, d.
  • Без интервала - Claude сам выбирает паузу от минуты до часа: дольше, когда ничего не происходит, чаще, когда работа кипит. Экономнее и отзывчивее.
  • Голый /loop запускает встроенный «дежурный» режим: доделать незаконченное, разобрать замечания и упавшие проверки, а если делать нечего - пройтись чисткой.
  • Остановить самопейсовый цикл - Esc.
✅

Встроенный дежурный режим не своевольничает, дословно из документации: «Claude не начинает новых инициатив вне этих рамок, а необратимые действия вроде публикации или удаления выполняются только если продолжают то, что переписка уже разрешила».

💡

Свой дежурный промпт кладётся в файл .claude/loop.md (проектный) или ~/.claude/loop.md (для всех проектов). Пиши его так, как набрал бы промпт руками. Держи коротким: всё сверх 25 000 байт обрезается, и ты этого не заметишь. Проектный файл важнее пользовательского. И он игнорируется, если ты указал промпт прямо в команде.

Тонкости расписания, которые ломают ожидания▼
  • Повторяющиеся задачи живут 7 дней и самоудаляются - защита от забытого вечного цикла. Нужно дольше - пересоздай или перенеси в Routines.
  • Планировщик специально сдвигает запуски, чтобы все сессии не били по серверам одновременно. Часовая задача на :00 может выстрелить в любой момент до :30. Время важно - ставь минуту, отличную от :00 и :30.
  • Пропущенные запуски не догоняются: если Claude был занят, задача сработает один раз, когда освободится, а не столько раз, сколько пропустила.
  • Времена по твоему местному поясу, а не по UTC.
  • Одноразовое напоминание заказывается обычными словами («напомни в 15:00 сделать то-то»), а не через /loop - иначе получится повторяющийся цикл.
  • Управление обычным языком: «какие у меня запланированные задачи?», «отмени проверку деплоя». Лимит - 50 задач на сессию.
Промпт: утренняя автономная проверка
Это задача, которая запускается автоматически - уточнить у меня ничего нельзя.

Что проверить: [КОНКРЕТНО - какие файлы, папки, источники].
Что считать нормой: [КРИТЕРИЙ].
Что делать с находками: [ЧТО ИМЕННО - выписать списком / поправить / только сообщить].
Куда положить результат: [ФАЙЛ ИЛИ КУДА].

Если данных для вывода не хватило - так и напиши, не додумывай.
Если находок нет - напиши одну строку «всё чисто», без пересказа проверенного.
6.2Безголовый режим: Claude как обычная утилита~12 мин▼

Урок «Routines and Headless» из курса in Action. Флаг -p превращает Claude в звено конвейера: подал данные на вход, получил ответ на выход, без всякого диалога.

Базовые примеры
# простой вопрос без диалога
claude -p "что делает этот проект?"

# подать данные через конвейер и записать ответ в файл
cat ошибка.txt | claude -p 'объясни коротко причину этой ошибки' > ответ.txt

# разрешить конкретные инструменты, чтобы не спрашивал
claude -p "приведи в порядок заголовки" --allowedTools "Read,Edit"

# структурированный ответ вместо текста
claude -p "перечисли основные разделы" --output-format json
Правило
Для скриптов и повторяемости добавляй --bare

Почему так. Дословно: «Bare-режим полезен для автоматизации и скриптов, где нужен одинаковый результат на каждой машине». Он пропускает автоподхват хуков, скиллов, команд, сабагентов, плагинов, внешних серверов, автопамяти и CLAUDE.md. Без него результат зависит от того, что настроено на конкретном компьютере.

Как применить. claude --bare -p "задача" --allowedTools "Read". Учти: в этом режиме Claude Code не читает твой вход по подписке - нужен ключ API в переменных окружения.

🚫

Главная опасность режима -p: без --bare сессия запускает хуки из настроек проекта и подключает его внешние серверы даже в папке, которой ты никогда не доверял. И при этом не показывает ни диалога доверия, ни запроса на подтверждение. Перед запуском по чужому репозиторию - либо просмотри его папку .claude/, либо стартуй с --bare.

Три формата вывода

ФорматЧто даёт
textОбычный текст, по умолчанию
jsonСтруктурированный ответ с метаданными: результат, идентификатор сессии, расход
stream-jsonПоток событий по мере генерации, для живого отображения
💡

Можно потребовать ответ строго по схеме: --output-format json вместе с --json-schema и описанием нужной структуры. Ответ придёт в отдельном поле, готовый к обработке - без разбора текста регулярками.

⚠️

Данные через конвейер ограничены 10 МБ. Больше - записывай в файл и ссылайся на путь в промпте. Ещё: сессии из claude -p не попадают в список выбора и не подхватываются через --continue - только по идентификатору.

✅

Скиллы и свои команды работают и в режиме -p: просто включи /имя-скилла в текст промпта, и Claude Code развернёт его перед запуском. Команды, которые существуют только в интерфейсе терминала, там недоступны.

6.3Плагины: упаковать свою настройку и раздать~12 мин▼

Финальный урок курса in Action ставит задачу так: «упакуй настройку, которой доверяешь, в плагин, который может установить вся твоя команда». Плагин собирает в один пакет команды, сабагентов, скиллы, хуки и подключения к внешним сервисам.

Правило
Двухшаговая логика: сначала добавить каталог, потом поставить плагин

Почему так. Люди добавляют маркетплейс и ждут, что плагины появятся. Не появятся: добавление каталога - это как подписаться на витрину, а не купить товар.

Как применить. Шаг 1: /plugin marketplace add имя-репозитория. Шаг 2: /plugin install имя-плагина@имя-каталога. Проверить: /plugin list.

⚠️

Читай итоговую строчку после установки. Если написано «Run /reload-plugins to activate» - плагин ещё не работает. Claude Code не всегда включает его сразу, потому что включение обнуляет кеш и следующий запрос перечитает весь диалог заново. Не выполнишь /reload-plugins - будешь звать команду и получать «неизвестная команда».

💡

Команды плагина называются через двоеточие: /имя-плагина:имя-команды. Не ищи их просто по имени - это защита от столкновений, когда два плагина приносят команду с одинаковым названием. Посмотреть, что принёс плагин: /plugin, вкладка Installed, Enter на плагине.

Правило
Выбирай область установки осознанно

Почему так. Поставишь в project то, что нужно лично тебе - навяжется всей команде через репозиторий. Поставишь в user то, что нужно команде - у коллег ничего не появится.

Как применить. user - себе во всех проектах. project - всей команде через репозиторий. local - себе только в этом проекте.

🚫

Главная ошибка при создании своего плагина: не клади папки со скиллами, агентами и хуками внутрь служебной папки .claude-plugin/ - там лежит только паспорт plugin.json. Claude Code ищет содержимое в корне папки плагина. Спрячешь внутрь - плагин установится пустым, и никакой ошибки ты не увидишь. Проверить структуру: claude plugin validate ./папка.

✅

Разрабатывай через claude --plugin-dir ./папка, а не через установку. Установка копирует плагин в кеш, и свежие правки туда не попадают. Флаг подхватывает папку напрямую - цикл «поправил, проверил» становится секундным. После правок в сессии: /reload-plugins.

🚫

Безопасность. Плагин запускает произвольный код с твоими правами: хуки выполняют команды, внешние серверы ходят в сеть, папка с исполняемыми файлами добавляется в системный путь. Anthropic не проверяет содержимое сторонних плагинов. Перед установкой смотри секцию «Will install» в карточке - там перечислено, что именно добавится, - и открой репозиторий: есть ли там хуки, серверы, исполняемые файлы.

6.4GitHub: ревью и ответы прямо в задачах~7 мин▼

Урок «GitHub Actions and Code Review». Ставится командой /install-github-app прямо из Claude Code. После установки Claude отвечает на упоминание @claude в задачах и запросах на слияние: разбирает изменения, оставляет замечания по строкам, может сам внести правки.

💡

Даже если ты не пишешь код, принцип переносится: это тот же цикл «Claude сам проверяет работу по заданным правилам», только площадка другая. То же самое ты делаешь скиллом-проверяющим и Stop-хуком у себя в папке.

✅

Утилиты командной строки внешних сервисов - самый экономный по контексту способ работы с ними. Поставленный gh позволяет Claude заводить задачи, открывать запросы на слияние и читать комментарии. Без него он будет ходить в неавторизованный API и упираться в лимиты.

Часть 7

Расширения: MCP, браузер, работа вне терминала

Урок MCP из курса 101 плюс всё, чего в курсах нет вообще: работа с десктопа, из браузера и с телефона, управление Chrome, публикация результата ссылкой и входящие события в живую сессию.

7.1MCP: подключение внешних сервисов~15 мин▼
Правило
Подключай сервер, когда ловишь себя на копировании данных из другого сервиса в чат

Почему так. MCP нужен ровно для этого: чтобы Claude читал и менял данные в системе напрямую, а не работал с тем, что ты вставил руками.

Как применить. Найди сервер нужного сервиса в каталоге Anthropic или в документации самого сервиса и выполни: claude mcp add --transport http имя https://адрес/mcp.

Четыре ловушки подключения

  • Для удалённых серверов всегда --transport http, а не sse: тот объявлен устаревшим и оставлен только для сервисов без HTTP-адреса.
  • Для локального сервера обязательны два дефиса -- перед командой запуска. Всё после них передаётся серверу нетронутым. Без них Claude Code попробует прочитать флаги сервера как свои и команда сломается.
  • Не ставь имя сервера сразу после --env: этот флаг принимает несколько пар подряд, и имя будет прочитано как ещё одна пара.
  • Область видимости нельзя поменять - только удалить и добавить заново.
Правило
После добавления обязательно проверь статус

Почему так. Строка «Added...» означает только то, что конфигурация записана. Учётные данные при добавлении не проверяются: можно вписать заглушку вместо токена, команда пройдёт, а сервер потом не подключится.

Как применить. claude mcp list - смотри значок: подключён, нужен вход, не достучались. Внутри сессии - команда /mcp.

💡

Область видимости - главное место, где спотыкаются: по умолчанию сервер виден только в той папке, где ты его добавлял. Открыл другой проект - «серверы не настроены». Нужен везде - --scope user. Нужен команде - --scope project (запишется в файл проекта и уедет в репозиторий).

🚫

Никогда не вписывай токены прямо в файл проекта - он коммитится, и ключ уедет всем, у кого есть доступ. Используй подстановку переменных окружения.

🚫

Безопасность: серверы, которые тянут внешний контент, открывают тебя под подмешивание чужих инструкций - текст со стороны может содержать команды, которые Claude примет за твои. А локальный сервер - это просто программа, запускаемая на твоей машине. Бери серверы из проверенного каталога или официальные от самих сервисов.

⚠️

Не подключай десятки серверов «на всякий случай»: каждый съедает место в контексте - имена его инструментов и инструкции грузятся в каждую сессию.

✅

Ресурсы сервера вставляются через @, как файлы, а его готовые сценарии появляются в меню команд наравне с твоими. Так ты даёшь Claude конкретный объект, а не заставляешь искать.

💡

Для сервисов с логином порядок такой: сначала добавить сервер, потом войти через /mcp → Authenticate. Статус «нужен вход» сразу после добавления - это нормально, а не ошибка.

7.2Вне терминала: десктоп, веб, телефон~10 мин▼
Главная развилка
Где физически должна выполняться работа - на твоём компьютере или в облаке

Почему так. Это единственный вопрос, который реально меняет правила. На твоём компьютере Claude видит твои файлы, настройки, подключённые сервисы и CLAUDE.md - но работа умирает, когда ты закрываешь ноутбук. В облаке нет ничего твоего, кроме репозитория, зато работа продолжается с закрытой крышкой.

Как применить. Нужны личные файлы вне репозитория, твои подключения и твои папки - это локальная работа, облако не подойдёт.

✅

Десктоп-приложение - тот же Claude Code, только с окном. Ставить ничего отдельно не надо: движок один. Оно читает те же CLAUDE.md, те же настройки, те же скиллы и хуки. То есть вся уже настроенная система переезжает в окно бесплатно. Можно держать открытыми терминал и приложение одновременно на одном проекте: история сессий раздельная, конфигурация общая.

🚫

Работать надо во вкладке Code, не в Chat и не в Cowork - это три разных инструмента в одном приложении. Chat - обычный разговор без доступа к файлам. Cowork - автономный агент в изолированном окружении. Code - тот самый Claude Code с прямым доступом к твоим файлам. Откроешь не ту вкладку - получишь Claude, который физически не видит твою папку, и решишь, что приложение сломано.

💡

Прямая рекомендация документации для десктопа: сложную задачу начинай в режиме Plan, потом переключайся в Accept edits. Так ты утверждаешь подход раньше, чем он тронул хоть один файл. Переключение - Cmd+Shift+M. Важно: выбор режима в десктопе запоминается по папке и перебивает настройку из файла.

⚠️

На Windows обязателен Git for Windows, иначе локальные сессии в приложении не запустятся. После установки перезапусти приложение.

7.3Claude управляет браузером~10 мин▼

Claude открывает вкладки, кликает, заполняет формы, вытаскивает данные - в твоём настоящем браузере под твоими логинами. Никаких коннекторов не нужно: он просто заходит в открытый сервис так же, как ты.

Правило
Режим включается флагом при запуске: claude --chrome

Почему так. Без флага браузерные инструменты вообще не загружены, и Claude физически не может открыть вкладку. Он не поленился - у него нет такой кнопки.

Как применить. До первого запуска нужны три вещи: Chromium-браузер, расширение «Claude in Chrome», и вход через /login аккаунтом Anthropic. Вход по ключу API не годится: Claude Code сам держит интеграцию выключенной, потому что расширение не умеет авторизоваться такими ключами.

🚫

Это одновременно суперсила и главный риск. Всё, куда ты залогинен в Chrome, потенциально доступно Claude. Перед браузерной сессией закрой лишние вкладки с чувствительными данными и ограничь список сайтов в настройках самого расширения - права по сайтам наследуются оттуда, а не из Claude Code.

✅

Всё видно в реальном времени, и на логине с капчей Claude останавливается сам. Это не скрытый бот в фоне: ты смотришь, как двигается курсор, и можешь вмешаться. Упрётся в форму входа - поставит задачу на паузу и попросит тебя сделать это руками.

💡

/chrome - пульт управления связкой: статус, переподключение расширения, выбор браузера, автозапуск. Девяносто процентов проблем чинятся здесь. Но не включай «по умолчанию» без нужды: браузерные инструменты грузятся в каждую сессию и съедают контекст, даже когда ты просто правишь текст.

7.4Артефакты: результат сессии живой страницей~8 мин▼
Правило
Артефакт - когда результат легче посмотреть, чем прочитать построчно

Почему так. Если результат - таблица цифр, сравнение вариантов, диаграмма или доска задач, текст в терминале теряет половину смысла: его нельзя прокрутить, кликнуть, отдать другому ссылкой. Для длинного связного текста, который всё равно читаешь сверху вниз, артефакт выигрыша не даёт, а токенов съедает больше.

Как применить. Отдельной команды нет - просто скажи словами: «сделай артефакт, который...». Claude может опубликовать страницу и сам, но если нужна гарантия - скажи прямо.

✅

Артефакт - живая страница, а не одноразовый экспорт. Обновление идёт по тому же адресу: ссылка, которую ты отдал вчера, показывает сегодняшнюю версию, и у всех открытых вкладок обновится на месте.

⚠️

Публикация - действие с внешним эффектом: файл выгружается на серверы Anthropic. Первый раз спросит разрешение, дальше переиздания той же страницы не спрашивают. Но спросит повторно, если страница получила право ходить за данными или если ты успел поделиться ею с кем-то - цена ошибки выросла.

💡

Если не назвать место, Claude запишет страницу во временную папку вне твоего проекта и опубликует оттуда. Хочешь, чтобы файл лежал у тебя - скажи, куда положить.

7.5Каналы: входящие события в живую сессию~8 мин▼

Возможность, которой нет ни в одном курсе: Claude Code принимает входящие сообщения прямо в работающую сессию - из мессенджера, от вебхука, из результатов сборки. Пишешь ему с телефона, он работает в твоей папке и отвечает туда же.

Правило
Канал не включается сам - его надо назвать флагом при запуске

Почему так. Дословно: «быть прописанным в конфигурации недостаточно, чтобы слать сообщения: сервер должен быть назван в флаге». Это защита - ты каждый раз осознанно решаешь, кто может писать в твою сессию.

Как применить. Запускай Claude Code с флагом --channels и именем канала. Несколько - через пробел.

🚫

Сразу после привязки закрой доступ списком разрешённых. По умолчанию режим сопряжения: любой, кто найдёт твоего бота, получит код и попытку достучаться. Незакрытый канал - это прямой путь внедрения чужих инструкций в сессию, у которой открыты твои файлы.

🚫

И самое важное: «любой, кто может отвечать через канал, может одобрять или запрещать использование инструментов в твоей сессии». Добавляя человека в список, ты даёшь ему право разрешить Claude выполнить любую команду на твоём компьютере, а не просто поболтать. Держи в списке только свои аккаунты.

⚠️

События приходят только в открытую сессию. Канал не будит новую сессию и не копит сообщения. Закрыл терминал - бот молчит, и ты будешь думать, что сломался токен. Для режима «пока меня нет» держи Claude Code в постоянном окне.

💡

Ответ увидишь в мессенджере, а не в терминале - там будет только входящая строка и отметка об отправке. Люди пугаются, что «Claude ничего не написал».

⚠️

Запрос разрешения останавливает сессию, пока ты не ответишь. На телефоне ты об этом не узнаешь - будет выглядеть как «Claude завис». Каналы с пересылкой запросов решают это: приходит запрос с коротким кодом, отвечаешь «yes» или «no» с этим кодом.

Часть 8

Безопасность, расход, починка

В курсах этого почти нет, а без этого работать нельзя. Три темы: что Claude физически может достать на твоём компьютере, куда утекают деньги и лимиты, и что делать, когда всё сломалось.

8.1Безопасность: где проходят границы~15 мин▼
Правило
Запомни асимметрию: пишет только в рабочую папку, читает почти всё

Почему так. Это самая частая ошибка ожиданий. Запись разрешена в текущую папку, явно добавленные папки и временную папку сессии. А чтение по умолчанию открыто по всему компьютеру, кроме отдельных запрещённых каталогов - то есть файлы с ключами и учётными данными в домашней папке по умолчанию читаются.

Как применить. Если у тебя есть личные папки, которые Claude вообще не должен видеть, закрой их явно - правилами запрета в настройках. Надежда «он туда не полезет» защитой не является.

🚫

Встроенного списка запрещённых секретов не существует - дословно: «There is no built-in credential deny list». Ограничено ровно то, что ты перечислил сам. И ещё: команды наследуют окружение родительского процесса вместе со всеми токенами, которые там лежат.

Правило
Не начинай с «разрешить всё» - начни с песочницы

Почему так. Флаг полного отключения вопросов убирает единственную защиту, и остаётся только граница изоляции. Документация требует запускать такие сессии только внутри контейнера или виртуальной машины. Важная деталь: одной встроенной песочницы для команд недостаточно - она ограничивает только команды оболочки, а файловые инструменты, внешние серверы и хуки работают вне её.

Как применить. Команда /sandbox открывает панель: режим, разрешён ли выход за границу, какие правила реально применились.

💡

Два слоя, которые надо различать: разрешения решают «запускать ли действие», песочница решает «докуда оно дотянется». Это независимые механизмы, и настраивать надо оба.

⚠️

Не расширяй список разрешённых доменов «на всякий случай». Отдельное предупреждение документации: разрешение широких доменов создаёт путь для утечки данных, потому что решение принимается по имени хоста, которое сообщает сам клиент.

✅

Если инструменту токен всё-таки нужен - есть режим маскирования вместо запрета: команда видит подставное значение, а настоящий токен подставляется уже на выходе и только для перечисленных адресов. Сама команда и её логи настоящий секрет никогда не держат.

Промпт: закрыть личное от чтения
Настрой мне границы доступа так, чтобы ты не мог читать ничего за пределами рабочих папок.

1. Покажи сначала, что тебе сейчас доступно на чтение и на запись - честно, включая домашнюю папку.
2. Предложи конфигурацию, которая закрывает домашний каталог целиком и оставляет открытыми только мои рабочие папки. Перечисли, какие папки оставляем, и спроси меня, всё ли учтено.
3. Отдельно закрой файлы с ключами и учётными данными, и переменные окружения с токенами.
4. После настройки проверь вживую: попробуй прочитать что-нибудь из закрытой зоны и покажи, что доступа нет.

Ничего не применяй, пока я не подтвержу конфигурацию.
8.2Куда уходят лимиты~10 мин▼
🎯

Документация называет две главные причины перерасхода прямым текстом: длинные незачищенные сессии и Opus, оставленный моделью по умолчанию.

Если ты на Pro или Max, не смотри на доллары в /usage как на счёт. Дословно: «блок Session показывает расход токенов API и предназначен для пользователей API. 💡

Полезное про диагностику расхода: /usage с клавишами d и w показывает разбор за сутки и неделю - в том числе по скиллам, сабагентам, плагинам и серверам, и флаги вроде «длинный контекст» или «промахи кеша», если они дают больше 10% расхода. А /insights собирает отчёт по последним сессиям: над чем работаешь, где буксуешь, что попробовать.

⚠️

Подключение или отключение внешнего сервера посреди сессии сбрасывает кеш и делает следующий ход дороже. Как и смена модели или уровня усилия.

8.3Когда что-то сломалось: порядок действий~10 мин▼

Документация даёт чёткую лестницу диагностики - от дешёвого к дорогому. Не гадай, иди по ней.

1

/doctor - единственная команда, которая ставит диагноз по всем фронтам сразу: здоровье установки, дубли и остатки прошлых установок, проблемы с путями, нечитаемые настройки, неиспользуемые скиллы и серверы с их ценой в контексте, медленные хуки, дубли CLAUDE.md, повторяющиеся имена сабагентов. Сначала показывает находки и спрашивает подтверждение, и только потом меняет. Если Claude вообще не стартует - claude doctor прямо в терминале.

2

claude --safe-mode - стерильная сессия. Гасит разом CLAUDE.md, скиллы, плагины, хуки, внешние серверы, свои команды и агенты, стили, статус-строку и автопамять. Чистое сравнение: пропало - виновата твоя надстройка, осталось - причина снаружи. Это же первый шаг при высоком расходе памяти.

3

Полностью пустая конфигурация. Safe mode всё ещё читает твои файлы настроек. Чтобы исключить и их - запустить с пустой папкой конфигурации из папки, где нет ни настроек, ни CLAUDE.md. Признак, что чистая папка подхватилась: появятся экраны первоначальной настройки. Проблема пропала - причина в твоих файлах, возвращай их по одному.

✅

Claude завис - жми Ctrl+C, и не бойся закрыть терминал. Документация прямо: «перезапуск не теряет твой разговор». Многие боятся закрывать окно и ждут часами.

Тормозит и ест память - официальный порядок

  1. /compact, чтобы уменьшить контекст. Ответ «Not enough messages to compact» значит, что реплик слишком мало для сжатия - так бывает даже при полном контексте, если его забила одна большая вставка.
  2. Перезапускать Claude Code между крупными задачами.
  3. Добавить большие служебные папки в игнор-лист, чтобы он их не обходил.
  4. Запуститься в стерильном режиме и проверить, не виноват ли плагин, сервер или хук.
🚫

Если снимаешь дамп памяти для отчёта об ошибке - наружу отдавай только файл диагностики с цифрами. Второй файл, снимок памяти, содержит каждую строку из памяти процесса: весь твой разговор целиком и учётные данные. Отдельное предупреждение документации: не прикладывать его к публичным обращениям. Для тебя это критично - там могут оказаться материалы учеников и переписки.

Промпт: диагностика по официальной лестнице
У меня проблема: [ОПИШИ, ЧТО ИМЕННО НЕ ТАК].

Пройди официальную лестницу диагностики Claude Code по порядку и на каждом шаге говори, что нашёл:

1. Запусти /doctor и покажи находки. Ничего не чини без моего подтверждения.
2. Если причина не нашлась - объясни, как мне запуститься в стерильном режиме, и что именно это исключит.
3. Если и там воспроизводится - объясни, как запустить сессию с полностью пустой конфигурацией.

По каждому шагу скажи простыми словами, что мы проверяем и что будет означать результат.

9.6Чек-лист: что настроить в первую неделюитог▼

Порядок из курсов: сначала контроль, потом правила, потом автоматизация.

1

Запреты в личных настройках. Что нельзя никогда - в ~/.claude/settings.json, оттуда это не перебьёт ни один проект.

2

Хук-замок на критичное. То, что обязано соблюдаться всегда, - хуком, а не текстом. Проверить через /hooks в новом чате.

3

Звуковые уведомления на события «готово» и «нужен ты» - два разных звука.

4

CLAUDE.md через /init, потом вычистить до 200 строк вопросом «если удалю - начнёт ошибаться?».

5

Строка состояния с процентом контекста - командой /statusline словами.

6

Порог автосжатия заранее через /autocompact, чтобы не срабатывало посреди сложного шага.

7

Первый скилл из процедуры, которую повторяешь чаще всего.

8

Первый сабагент на задачу, где надо много прочитать, а вывод короткий.

9

Привычка /clear между несвязанными задачами. Самая дешёвая и самая недооценённая.

10

Привычка требовать доказательство вместо слова «готово».

Что запомнить, если забудешь всё остальное

Дай Claude проверку, которую он может запустить сам - это разница между сессией, которую ты смотришь, и сессией, от которой можно отойти.

Контекст - самый дорогой ресурс. Почти все приёмы всех четырёх курсов выведены из одного факта: окно заполняется быстро, и качество падает по мере заполнения.

Просьба, фильтр и замок - разные вещи. CLAUDE.md просит, разрешения фильтруют, хук запрещает физически. Критичное закрывай всеми тремя.
